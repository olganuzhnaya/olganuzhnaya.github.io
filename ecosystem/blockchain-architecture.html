BLOCKCHAIN ARCHITECTURE

The Architecture of Blockchain Systems

How networks, data structures, execution environments and protocol layers work together.

INTRODUCTION

This study examines blockchain architecture as an integrated system of networking, data structures, transaction processing, execution, state management and consensus. It compares the architectural approaches of Bitcoin, Ethereum and Cardano, while exploring modular design, security considerations and the trade-offs that shape distributed systems.

01. The Architecture Of A Blockchain System

1.1 From Individual Components to an Integrated System

A blockchain system can be understood as a collection of interconnected components that perform different functions. These functions include:

  • Networking: enabling computers to communicate and exchange information.
  • Transaction processing: receiving and handling requests submitted by users and applications.
  • Data organisation: arranging transactions and related information into structures that can be stored and verified.
  • Execution: applying protocol rules to determine the effects of transactions.
  • Consensus: coordinating participants around the accepted ordering of blocks and the network's history or state.
  • Storage: maintaining the information required to operate and verify the system.

These functions are closely connected, but they are not interchangeable. For example, communication between computers does not itself establish that a transaction is valid. Similarly, executing a transaction does not, by itself, establish agreement across the entire network. The architecture defines how these responsibilities are coordinated.

1.2 A Functional View of Blockchain Architecture

For analytical purposes, blockchain architecture can be examined through several functional areas.

Network layer

This area is responsible for communication between participating computers. It enables information such as transactions and proposed blocks to move between network participants.

Data and ledger layer

This area concerns how information is represented, organised and maintained. It includes transaction records, block structures, cryptographic commitments and the ledger's current state.

Execution layer

In programmable blockchain systems, this area processes transactions and executes operations according to the network's rules. Execution may change account balances, contract storage or other elements of the system's state.

Consensus layer

This area coordinates the network's acceptance of blocks and the ordering of its history. Its mechanisms and security assumptions differ between blockchain protocols. These areas provide a useful way to analyse blockchain systems. They should not be interpreted as a universal technical blueprint: some networks combine responsibilities, while others separate them into distinct software components or protocol layers.

1.3 Different Networks, Different Architectures

Bitcoin, Ethereum and Cardano demonstrate why architectural comparisons must account for protocol-specific design. Bitcoin uses an unspent transaction output model (UTXO). Its architecture relies on transactions that consume previously created outputs and produce new outputs. Ethereum uses an account-based state model. Transactions can transfer value, deploy smart contracts or request the execution of contract code. Its architecture separates consensus responsibilities from execution responsibilities through specialised clients. Cardano describes its architecture through four principal layers: ledger, consensus, networking and scripting. These layers have defined responsibilities, even though a running node integrates their functions. These examples illustrate that blockchain architecture is not determined simply by the use of blocks or cryptography. It is shaped by the rules governing data, execution, communication and coordination.

1.4 Why Architecture Matters

Architectural decisions influence the properties and limitations of a blockchain system. They affect:

  • how transactions travel through the network;
  • how quickly information becomes available to participants;
  • how network state is updated and verified;
  • what resources nodes require;
  • how the system responds to failures or competing blocks;
  • how software upgrades and new capabilities are introduced;
  • which security assumptions participants must accept.

No architecture optimises every property simultaneously. A design that prioritises independent verification may impose greater storage or computational requirements. A design that separates functions into multiple layers may improve flexibility but introduce additional coordination requirements. Understanding these trade-offs is essential when evaluating blockchain networks beyond their marketing descriptions or headline performance claims.

02. Peer-To-Peer Network Architecture

2.1 What Is a Peer-to-Peer Network?

A peer-to-peer (P2P) network is a communication model in which participating computers, known as peers, exchange information directly with one another without depending on a single central server to coordinate every interaction. In a traditional client-server model, a central server provides services or distributes information to connected clients. The clients generally communicate through that central infrastructure. In a peer-to-peer network, participating computers can communicate with multiple other computers. Depending on the system, a peer may both request information and provide information to other participants. Blockchain networks use this approach to distribute transactions, blocks and other protocol messages among their participants. However, peer-to-peer does not mean that every computer is identical or performs exactly the same tasks. Different nodes may have different software configurations, storage capabilities, responsibilities and connection patterns.

2.2 How Nodes Discover One Another

Before a computer can exchange information with other participants, it needs to establish network connections. This process is known as peer discovery. A new node may obtain information about potential peers through several mechanisms:

  • predefined network addresses included in its software;
  • addresses supplied by previously known peers;
  • dedicated discovery protocols;
  • distributed records containing information about other participants.

For example, Ethereum execution clients use discovery protocols to locate other nodes. Bootnodes can help a newly started client find initial peers, but they do not act as central authorities controlling the network. After establishing initial connections, a node can discover additional participants and maintain its own set of network connections. Peer discovery is therefore an entry point into the network, not a process that requires every participant to connect to every other participant.

2.3 Network Topology and Peer Connections

Network topology describes how computers are connected and how information can travel between them. A peer-to-peer blockchain network generally forms a distributed graph of connections. Each node maintains connections with a limited number of peers rather than establishing a direct connection with every node in the entire network. This arrangement has several practical advantages:

  • it reduces the number of connections each computer must maintain;
  • it allows information to travel through multiple independent paths;
  • it supports network expansion as new participants join;
  • it avoids requiring one central computer to distribute every message.

The exact number of connections and the rules for selecting peers depend on the particular network implementation. A distributed network can also experience changing connections as nodes join, disconnect, restart or become temporarily unavailable.

2.4 How Information Travels Across the Network

Blockchain networks use different communication mechanisms to distribute information. One important approach is commonly called gossip propagation. When a node receives new information, it can announce that information to selected peers. Those peers may then relay it to their own connections. Through repeated propagation, information can spread across a large portion of the network. For example, when a Bitcoin node receives a transaction, it checks the transaction according to its applicable rules before relaying it to other peers. Ethereum also uses peer-to-peer networking to propagate transactions and blocks, although its execution and consensus networks have distinct communication responsibilities. Gossip propagation does not mean that every node receives every message at exactly the same moment. Network latency, connection quality, software configuration and propagation rules influence when information becomes available to different participants.

2.5 Direct Communication Does Not Mean Global Agreement

An important distinction must be made between communication and consensus. A node can receive information from another computer without automatically accepting that information as valid. For example, a peer may announce a transaction or a proposed block. The receiving node must still apply the relevant protocol rules. A message being transmitted across a network does not establish that it is correct, authorised or accepted as part of the blockchain's history. Networking enables information exchange. Validation checks compliance with protocol rules. Consensus coordinates agreement about the accepted chain or state. These are separate functions that work together.

2.6 Different P2P Designs Across Blockchain Networks

Although Bitcoin, Ethereum and Cardano all use peer-to-peer communication, their networking implementations are not identical.

Bitcoin

Bitcoin full nodes use the Bitcoin peer-to-peer protocol to exchange transactions and blocks. Full nodes independently verify received blockchain data before relaying it to other peers.

Ethereum

Ethereum uses different networking stacks for its execution and consensus clients. These stacks support peer discovery, secure communication and the propagation of transactions, blocks and consensus-related messages.

Cardano

Cardano uses a networking architecture designed around peer selection, connection management and the diffusion of transactions and blocks. Its node-to-node communication includes specialised protocols for chain synchronisation, block retrieval and transaction submission. These examples demonstrate that peer-to-peer networking is a broad architectural principle rather than one universal communication protocol.

2.7 Security and Operational Challenges

Distributed communication introduces several technical challenges.

Unreliable connections

Nodes may disconnect, experience delays or become temporarily unreachable. Network protocols must handle these conditions without assuming that every participant remains continuously available.

Malicious participants

A peer may send misleading, invalid or excessive messages. Nodes need mechanisms to reject invalid information and protect their resources.

Network isolation

An attacker may attempt to restrict a node's connections so that it communicates primarily with attacker-controlled peers. This is commonly associated with eclipse attacks.

Information propagation delays

Different participants may receive the same transaction or block at different times. Such delays can influence transaction visibility and the temporary presence of competing block candidates.

Resource consumption

Maintaining connections and processing messages requires bandwidth, memory and computing resources. Network implementations must manage these requirements carefully. The security of a peer-to-peer network therefore depends not only on cryptography but also on connection management, protocol design, software implementation and the diversity of network participants.

2.8 Why Peer-to-Peer Networking Matters

Peer-to-peer architecture allows blockchain systems to distribute communication and information exchange across independently operated computers. It reduces reliance on a single communication authority and provides multiple paths through which information can travel. Nevertheless, decentralised communication alone does not guarantee decentralised ownership, governance, validation or economic power. These properties depend on additional aspects of the system, including who operates nodes, who can participate in consensus, how software is maintained and how protocol changes are coordinated. Understanding the networking layer is therefore essential for evaluating the actual structure of a blockchain rather than relying only on the label "decentralised."

Research Note

Peer-to-peer networking provides the communication infrastructure through which blockchain participants exchange information. It does not independently determine whether transactions are valid or which blocks become part of the accepted ledger history. Those responsibilities belong to other parts of the system, including transaction validation, execution and consensus. The distinction between communication, verification and agreement is fundamental to understanding blockchain architecture. Crypto Atlas treats decentralisation as a property that must be examined through the actual design and operation of a network, rather than assumed from the presence of peer-to-peer connections alone.

03. Transaction Lifecycle

How a transaction moves from a user's wallet into a blockchain and becomes part of the network's accepted history.

3.1 A Transaction Is More Than a Transfer

When a user sends cryptocurrency, the process may appear simple: enter a recipient's address, specify an amount and press Send. Behind this action, however, a sequence of technical operations takes place. The wallet prepares a transaction, cryptographically authorises it, and submits it to a blockchain node. The network checks the transaction according to its protocol rules. If accepted for further processing, it may be included in a block. The network then verifies that block and updates its accepted record of transactions. A transaction is therefore not simply a message travelling from one wallet to another. It is a structured instruction that must satisfy the rules of a particular blockchain. The exact process differs between networks, but several general stages can be identified.

3.2 Stage One — Transaction Construction

The process begins in the user's wallet. The wallet prepares the information required to describe the intended operation. Depending on the blockchain, this may include:

  • The sender's address or account.
  • The recipient's address.
  • The amount being transferred.
  • The transaction fee.
  • Additional information required by the protocol.
  • References to existing funds or previous transactions, where applicable.

The structure of this information depends on the network. In Bitcoin, a wallet generally selects one or more unspent transaction outputs (UTXOs) as inputs. It creates outputs for the recipient and, when necessary, returns the remaining value to the sender as change. In Ethereum, a transaction uses an account-based structure. It includes information such as the sender, recipient, value, account nonce and gas-related parameters. It may also contain data instructing a smart contract to perform an operation. Cardano also uses a UTXO-based model, with its own transaction structure and validation rules. Its transactions can include inputs, outputs, fees, witnesses and other fields. These differences are not merely technical details. They reflect different ways of representing ownership, available funds and changes to the ledger.

3.3 Stage Two — Cryptographic Signing

Once the transaction has been constructed, it must be authorised. The wallet uses the appropriate private key to create a digital signature. This signature allows network participants to verify that the transaction was authorised by the holder of the relevant cryptographic credentials. The private key itself is not sent across the network. This distinction is fundamental:

  • The private key is used to authorise the transaction.
  • The digital signature is included in the transaction.
  • Other participants can verify the signature using the corresponding public information.

Signing does not mean that the transaction has already been accepted by the blockchain. It means that the transaction carries cryptographic evidence of authorisation. The transaction must still pass the network's validation procedures.

3.4 Stage Three — Submission to the Network

After signing, the wallet submits the transaction to a blockchain node, either directly or through a service provider that communicates with the network. The node receives the transaction and begins checking it. The initial checks depend on the protocol, but may include:

  • Whether the transaction has a valid structure.
  • Whether the required signatures are correct.
  • Whether the sender is authorised to spend the referenced funds.
  • Whether the transaction follows applicable fee rules.
  • Whether the transaction conflicts with existing network data.
  • Whether other protocol-specific conditions are satisfied.

A transaction that fails essential checks may be rejected before it reaches the next stage. An important distinction is that a node's decision to accept a transaction for relay or temporary storage is not the same as the network's final acceptance of a block. These are separate processes with different responsibilities.

3.5 Stage Four — Transaction Propagation

If the node accepts the transaction for relay, it can share information about it with connected peers. Other nodes receive the transaction, perform their own checks and may relay it further. This is where the peer-to-peer architecture discussed in the previous section becomes important. The transaction can spread through the network without requiring every participant to communicate directly with the original sender. However, propagation does not mean that every node receives the transaction at precisely the same moment. Different nodes may have different views of the transactions currently awaiting inclusion in blocks. A transaction may therefore be visible to some network participants before others have received it.

3.6 Stage Five — Waiting for Block Inclusion

Before a transaction becomes part of the blockchain's accepted history, it generally waits to be selected for inclusion in a block. Many blockchain systems maintain a temporary collection of transactions waiting for processing. In Bitcoin this is commonly called the mempool. Ethereum clients use transaction pools, which may distinguish between transactions ready for inclusion and those waiting for earlier account transactions. These pools are not necessarily one shared global database. Individual nodes can maintain different collections of pending transactions. During periods of high demand, more transactions may be waiting than can fit into the next block. The network's fee mechanism can influence which transactions are selected. In Bitcoin, miners commonly consider the fee rate of transactions. In Ethereum, the priority fee can influence a validator's incentive to include a transaction. However, paying a higher fee does not create an absolute guarantee of immediate inclusion. A transaction can remain pending while network conditions change. It may also be dropped from a node's transaction pool or become invalid if the conditions required for its execution are no longer satisfied.

3.7 Stage Six — Selection and Block Inclusion

At this stage, a participant responsible for producing a block selects transactions according to the network's rules and its own selection policies. The block producer may be:

  • A miner in a Proof-of-Work network.
  • A validator in a Proof-of-Stake network.
  • Another authorised block-producing participant in a different consensus design.

The selected transactions are organised into a candidate block. Inclusion in a block is a major milestone, but it does not mean that every network has reached the same level of finality. The block must still be checked and accepted according to the blockchain's consensus rules.

3.8 Stage Seven — Independent Block Validation

A proposed block is propagated to other network participants. Nodes that receive it verify whether it follows the protocol rules. Depending on the network, these checks can include:

  • Whether the block is correctly connected to the existing chain.
  • Whether its transactions are valid.
  • Whether signatures and spending conditions are satisfied.
  • Whether the block respects size, weight or computational limits.
  • Whether the block producer followed the applicable consensus rules.
  • Whether the resulting ledger state is correct.

In Ethereum, for example, execution clients process the transactions in a block and verify that the resulting state matches the state commitment included in the block. The important principle is that block producers do not simply ask everyone else to trust their work. Independent participants verify the proposed block using the rules of the protocol. A block that violates those rules is not accepted by a correctly operating node.

3.9 Stage Eight — Ledger Update and Confirmation

When a valid block becomes part of the accepted chain, the transaction is recorded in the blockchain. The resulting ledger state changes according to the transaction's meaning. In a simple transfer, the recipient may now have control over the newly received funds. In a smart-contract interaction, the transaction may also change contract storage, token balances or other application data. The wallet or blockchain explorer can then display the transaction as included in a block. However, block inclusion, confirmation and finality should not be treated as identical concepts. In Bitcoin, a transaction included in a block receives its first confirmation. Each subsequent block added on top increases the number of confirmations and makes reversal increasingly difficult, although Proof-of-Work does not provide the same deterministic finality mechanism as some other consensus designs. In Ethereum, blocks progress through consensus stages such as justified and finalized. Finalization provides a stronger protocol-level guarantee than simply observing that a transaction has appeared in a block. Cardano distinguishes between transaction confirmation and the point at which the chain is considered stable under its protocol parameters. Additional blocks increase confidence that the transaction will not be rolled back. The practical meaning of confirmation therefore depends on the network.

3.10 What Can Go Wrong?

A transaction does not always complete the process successfully. Several situations are possible: Insufficient or invalid transaction data. A transaction may fail initial validation because its structure, signature or other required information is incorrect. Conflicting transactions. Another transaction may spend the same funds first or otherwise make the original transaction invalid. Low transaction fees. A transaction may remain pending if block producers have more attractive transactions available. Network congestion. High demand can increase waiting times and make inclusion less predictable. Execution failure. In a smart-contract network, a transaction can be included in a block but fail during execution. On Ethereum, for example, a reverted transaction does not apply its intended state changes, but the sender still pays for the computation already performed. Chain reorganisation. A block that was temporarily part of a node's preferred chain may later be replaced by another valid chain. Transactions from the displaced block may return to a pending state or be included elsewhere, depending on their validity. These cases show why a wallet's initial notification should not always be interpreted as proof that the intended operation has been completed.

3.11 Three Networks, Three Transaction Models

The broad lifecycle is useful for understanding blockchain systems, but the details are different.

Bitcoin

A wallet constructs a UTXO-based transaction and signs it. Nodes verify it and may relay it to peers. Miners select transactions for candidate blocks. Full nodes independently verify the blocks, and additional confirmations strengthen confidence in the recorded payment.

Ethereum

A user submits a signed account-based transaction. The transaction is propagated and may enter a transaction pool. A validator includes it in a block, and execution clients process it to calculate the resulting state. The block then progresses through the network's consensus process towards finality.

Cardano

A transaction is constructed using the eUTXO model, signed with the required witnesses and submitted to a node or service provider. After validation, it can enter a mempool. A stake pool operator selected to produce a block may include it, after which the block is propagated and checked by the network. The differences demonstrate that there is no single universal transaction-processing sequence that describes every blockchain in full detail. The general stages are comparable, but the underlying rules and data models remain network-specific.

3.12 Why the Transaction Lifecycle Matters

Understanding the transaction lifecycle helps explain several important questions:

  • Why does a wallet sometimes show Pending?
  • Why can a transaction take longer during periods of high network demand?
  • Why do transaction fees influence inclusion?
  • Why is a transaction checked by independent nodes?
  • Why can a transaction appear in a block before it reaches finality?
  • Why can a smart-contract transaction fail even after being included?

Most importantly, it clarifies that a blockchain transaction is not completed by a single computer or institution. It passes through a sequence of operations involving wallets, nodes, network communication, transaction validation, block production and consensus. Each stage contributes a different part of the process.

Research Note

A blockchain transaction moves through several distinct stages: construction, cryptographic authorisation, submission, propagation, validation, block inclusion and confirmation. These stages should not be confused. A signed transaction is not necessarily accepted by a node. A transaction accepted into a local pool is not yet part of the blockchain. Inclusion in a block does not always mean that the block has reached finality. The transaction lifecycle reveals how blockchain architecture coordinates individual instructions with a shared ledger. It also provides the foundation for understanding the next topics: transaction pools, block production, data structures and execution environments.

04. Mempool And Transaction Propagation

How pending transactions are stored, exchanged between nodes and prepared for inclusion in future blocks.

4.1 What Is a Mempool?

The term mempool comes from the words memory and pool. It describes a temporary collection of transactions that a blockchain node has received and accepted for further processing but that have not yet been included in the node's accepted blockchain. A mempool acts as a waiting area between transaction submission and block inclusion. It is important to understand that a mempool is not a permanent part of the blockchain. Transactions stored there are not yet recorded in the chain itself. More importantly, there is no single universal mempool shared by every participant. Each node maintains its own local transaction pool according to its software, protocol rules, available resources and current view of the blockchain. This means that two nodes connected to the same network may have different lists of pending transactions. The word mempool is therefore best understood as a general concept describing local transaction storage, rather than the name of one central network-wide database.

4.2 Why Does Every Node Have Its Own Mempool?

A blockchain network consists of independent computers communicating with one another. When a node receives a transaction, it checks the transaction according to its own validation rules. If the transaction is acceptable for its local pool, the node may store it and share it with connected peers. However, several factors can cause the local pools to differ. Different arrival times. Nodes do not receive every transaction simultaneously. A transaction may reach one node before another. Different network connections. Each node communicates with a limited number of peers. Its view of pending transactions depends partly on the information received through those connections. Different validation policies. Some nodes may apply different local admission or relay policies, even when they follow the same consensus rules. Different resource limits. Nodes have finite memory and storage resources. Their software may limit how many transactions or how much transaction data can be retained. Changes in the blockchain. When a new block is accepted, transactions included in that block are generally removed from the local mempool. Other transactions may also become invalid because the underlying ledger state has changed. As a result, the mempool of one node is not necessarily an exact copy of the mempool maintained by another. This is not a failure of decentralisation. It is a consequence of independent nodes maintaining their own local information.

4.3 How Are Transactions Shared Between Nodes?

A local mempool would be of limited use if transactions remained visible only to the node that first received them. Blockchain networks therefore use transaction propagation mechanisms to distribute pending transactions. The general idea is simple:

  1. A node receives a transaction.
  2. It checks whether the transaction is acceptable.
  3. It informs selected peers that it has information about the transaction.
  4. Peers that do not already have the transaction can request it.
  5. After receiving and checking it, they may relay it to their own peers.

This process allows transactions to spread through a distributed network without requiring every node to communicate directly with every other node. Bitcoin provides a clear example of this mechanism. Its peer-to-peer protocol uses messages such as inv, which announces the availability of a transaction, and getdata, which allows a peer to request the transaction itself. This approach helps nodes avoid repeatedly sending transaction data that their peers already possess. Ethereum also uses peer-to-peer transaction propagation. Nodes exchange pending transactions through the networking protocols used by Ethereum clients. Cardano uses its own node-to-node transaction submission protocol to exchange transactions between connected nodes. The implementation differs, but the purpose is similar: make valid pending transactions available to block-producing participants across the network.

4.4 Why Can Two Nodes See Different Transactions?

Imagine three nodes connected to one another:

  • Node A receives transaction X.
  • Node B receives transaction Y.
  • Node C has not yet received either transaction.

After information begins spreading, Node A may learn about Y, while Node B learns about X. Node C may receive both later. For a period of time, their local mempools can look different. Illustrative example — not a representation of a particular blockchain's actual network topology. This difference can also persist for reasons beyond ordinary network delay. A node may reject a transaction because it does not meet its local admission policy. Another node may accept it. One node may have removed an older transaction to make room for new ones, while another still retains it. Consequently, looking at one node's mempool does not reveal every unconfirmed transaction currently known to the entire network. A block producer can only select transactions available to it, subject to the rules and policies of its own implementation.

4.5 How Does a Transaction Queue Develop?

A queue develops when transactions arrive faster than block producers can include them in blocks. Every blockchain has limits on the amount of transaction data or computational work that can be included in a block. These limits mean that a block cannot contain an unlimited number of transactions. When demand is greater than available block capacity, some transactions must wait. Consider a simplified example:

  • A block can accommodate a limited amount of transaction data.
  • More transactions arrive than can fit into the next block.
  • The block producer selects a subset of available transactions.
  • The remaining transactions continue waiting, provided they remain valid and are retained by the node.

The next block may include some of those remaining transactions, but new transactions may also arrive in the meantime. This creates a dynamic queue rather than a fixed line in which every transaction advances at a predictable speed. The waiting time depends on several factors:

  • The amount of pending transaction activity.
  • The capacity of individual blocks.
  • The transaction's fee or priority under the network's rules.
  • The transaction's validity and dependencies.
  • The policies used by nodes and block producers.
  • Network conditions and the speed of transaction propagation.

A transaction can therefore remain pending even when the blockchain continues producing new blocks.

4.6 Transaction Fees and Mempool Competition

Transaction fees are an important part of how some blockchain networks manage limited block capacity. When many users want their transactions included, they compete for available space or computational resources. In Bitcoin, transactions are commonly compared using their fee rate — the fee paid relative to the transaction's virtual size. A transaction offering a higher fee rate may be more attractive to a miner because it can provide more fee revenue for the amount of block space it occupies. Bitcoin nodes also apply local relay and mempool policies. These policies influence which transactions they accept, retain and forward. In Ethereum, transaction fees use a different model. Transactions specify gas-related parameters, including a maximum fee and, under the EIP-1559 fee mechanism, a priority fee. The priority fee can influence the incentive for a validator or block builder to include a transaction. These systems should not be confused with a universal rule that every blockchain always processes the highest-fee transaction first. Fee mechanisms, local admission rules and block-production policies differ between networks. A fee can influence inclusion, but it does not guarantee an exact processing time.

4.7 Ethereum: Pending and Queued Transactions

Ethereum provides a useful example of how a transaction pool can organise transactions according to their readiness for execution. In Geth, the Ethereum execution client, the transaction pool distinguishes between two important categories:

Pending transactions

These are transactions that are ready to be processed and included in a future block, taking account of the account's expected transaction sequence.

Queued transactions

These are transactions that cannot yet be processed because an earlier transaction from the same account is missing or another required condition has not been met. Ethereum accounts use a field called a nonce. It is a sequential number that helps ensure transactions from an account are processed in the correct order. For example, suppose an account has three transactions:

  • Transaction 15
  • Transaction 16
  • Transaction 17

If transaction 15 is not available, transactions 16 and 17 cannot simply be processed as though the earlier transaction had already happened. They may remain queued until the missing transaction becomes available or the account's transaction sequence changes. This illustrates an important point: a transaction can be valid in its structure and signature but still not be ready for immediate execution. The exact management of pending and queued transactions depends on the Ethereum client implementation and its configuration.

4.8 Bitcoin: Mempool Policies and Transaction Replacement

Bitcoin provides another perspective. A Bitcoin node's mempool is a local collection of unconfirmed transactions that the node considers eligible for possible inclusion in a block. The mempool is temporary and has resource limits. When the pool reaches its configured limits, the node may remove transactions according to its eviction policies. The minimum fee rate required for a transaction to enter or remain in a particular node's mempool can also change with demand. This explains why a transaction might be visible to one Bitcoin node but not another. Bitcoin also supports transaction replacement under defined conditions. One example is Replace-by-Fee (RBF), which allows a sender to broadcast a replacement transaction that spends the same inputs but offers a more attractive fee, subject to the applicable replacement rules. This can be useful when a transaction is waiting too long because its original fee is no longer competitive. However, replacement is not the same as adding a second independent payment. The competing transactions cannot both spend the same UTXOs in the final accepted chain. A node's decision to accept or relay a replacement also depends on its policy rules.

4.9 Cardano: A Different Approach to the Mempool

Cardano illustrates why the term mempool should not imply that every blockchain uses the same queue design. The Cardano node maintains a bounded sequence of transactions that are valid against the ledger state associated with its current chain selection. Transactions are checked before being added to this local sequence. When the chain state changes, the mempool is synchronised and transactions that are no longer valid can be removed. The reference Cardano implementation maintains transactions in arrival order and uses a consistency model in which each transaction is checked against the state produced by the preceding transactions in the sequence. This design is important for Cardano's extended UTXO (eUTXO) model, where transactions can depend on outputs created by earlier transactions. When a block-producing node is selected to create a block, it can take a suitable sequence of transactions from its mempool, subject to block capacity and protocol limits. Unlike Ethereum's account nonce model, this is not simply a queue of sequential transactions from each account. Cardano's approach demonstrates that mempool organisation is closely connected to the blockchain's ledger model and transaction validation rules.

4.10 What Happens When the Mempool Changes?

A mempool is not a static waiting list. Its contents can change continuously. Several events can affect it. A transaction is included in a block. Once the node accepts a block containing a transaction, that transaction is removed from its pending pool. A transaction becomes invalid. For example, another accepted transaction may have already spent the same Bitcoin UTXO. A transaction is replaced. Under applicable network and client policies, a new transaction may replace an existing pending transaction. A transaction is evicted. A node may remove transactions to remain within its resource limits or apply its fee policies. A new block changes the ledger state. Transactions that depended on an earlier state may need to be checked again. A node receives new information. Transactions that were previously unknown may arrive through connected peers. These changes explain why a mempool explorer or node interface should be treated as a snapshot of a particular node's current view, not as a complete and permanent record of all pending network activity.

4.11 Mempool Is Not the Blockchain

The distinction between a mempool and the blockchain is fundamental. A transaction in a mempool is pending. It has not yet become part of the accepted blockchain history. A transaction included in a valid block has crossed an important boundary: it is now recorded in the chain selected by the node. However, the transaction's ultimate security still depends on the consensus and finality rules of the network. The mempool is therefore a temporary coordination mechanism. It helps nodes and block producers manage transactions before those transactions become part of the shared ledger history. It does not itself establish final ownership, guarantee inclusion or provide consensus.

4.12 Why Mempool Architecture Matters

Understanding mempools helps explain why blockchain networks behave differently under heavy demand. It also clarifies several practical questions:

  • Why can two block explorers show different numbers of pending transactions?
  • Why can a transaction be visible to one node but not another?
  • Why do transaction fees sometimes rise during periods of congestion?
  • Why can a transaction remain pending even while new blocks are being produced?
  • Why do Ethereum and Cardano organise pending transactions differently?
  • Why can a node remove a transaction that another node still retains?

The mempool connects the networking layer with transaction processing and block production. It is one of the mechanisms that allows independent nodes to exchange information while maintaining their own local views of pending activity.

Research Note

A mempool is a node-local, temporary collection of pending transactions. It is not a single global queue and does not form part of the permanent blockchain ledger. Transaction propagation allows nodes to exchange information about pending transactions, but network delays, peer connections, local policies, resource limits and validation rules can produce different mempool contents. Bitcoin, Ethereum and Cardano demonstrate different approaches to managing pending transactions. Their designs reflect differences in transaction models, fee mechanisms and ledger architecture. The next step is to examine how block-producing participants select transactions from the information available to them and organise those transactions into blocks.

05. Block Production And Ordering

How blockchain participants assemble blocks, select transactions and establish their order within the distributed ledger.

5.1 From Pending Transactions to a Candidate Block

A blockchain block is more than a container holding a list of transactions. It is a structured unit of data that connects new transactions to the existing blockchain history. Producing a block requires selecting eligible transactions, arranging them according to the network's rules, calculating the necessary data commitments and preparing the block for verification by other participants. The process begins with the information available to a block-producing participant. As discussed in the previous section, nodes maintain local collections of pending transactions. A block producer can select transactions from the pool available to it, but it does not necessarily have access to every pending transaction known across the entire network. The selected transactions form the basis of a candidate block. A candidate block is a proposed block that has not yet become part of the network's accepted chain. The way candidate blocks are created depends on the blockchain's consensus mechanism and architecture.

5.2 Who Is Allowed to Produce a Block?

Block production is coordinated by the blockchain's consensus protocol. Different networks assign this responsibility in different ways.

Bitcoin — Miners

Bitcoin uses Proof of Work. Miners compete to find a valid block header hash that satisfies the network's current difficulty target. Mining software constructs candidate blocks, while specialised hardware performs the repeated hashing calculations required by Proof of Work. A miner or mining pool that finds a valid result can broadcast its block to the network.

Ethereum — Validators

Ethereum uses Proof of Stake. A validator is selected to propose a block for a particular time slot. The selected validator is responsible for proposing a block that extends the chain according to the network's consensus rules. The validator's execution client provides transaction-processing information, while the consensus client participates in the Proof-of-Stake protocol.

Cardano — Stake Pool Operators

Cardano uses the Ouroboros Proof-of-Stake protocol. Stake pool operators maintain the infrastructure needed to participate in the network. A stake pool is eligible to produce a block when its leader-selection conditions are satisfied for a particular slot. The selected pool produces and signs a block that can be checked by other network participants. These systems differ in how block producers are selected, but all must ensure that proposed blocks satisfy the rules of the protocol.

5.3 How Are Transactions Selected?

A block producer cannot include an unlimited number of transactions. Each blockchain imposes limits on block size, weight, execution resources or other protocol-defined measures. The producer must therefore select a set of transactions that fits within the applicable limits. Several considerations may influence this selection:

  • Whether the transaction is valid.
  • Whether its required inputs or dependencies are available.
  • The amount of block space or computational resources it consumes.
  • The fees or incentives associated with including it.
  • The ordering constraints imposed by the protocol.
  • The block producer's local policies and selection strategy.

The exact selection method is not universal. In Bitcoin, miners commonly consider fee rates and transaction dependencies when selecting transactions for a candidate block. In Ethereum, transaction selection is connected to gas limits, fee incentives, account nonces and execution rules. Block builders may also consider additional economic opportunities when constructing transaction sequences. In Cardano, the selected transactions must be valid under the ledger rules and fit within the block's protocol limits. Their compatibility with the eUTXO ledger state is particularly important. A block producer is therefore not simply collecting transactions in the order they arrived. It is constructing a block that must satisfy technical, economic and protocol constraints.

5.4 Why Does Transaction Ordering Matter?

The order of transactions inside a block can affect how the network processes them. Consider a simplified example. A blockchain receives two transactions:

  • Transaction A changes the balance or state of a particular account.
  • Transaction B attempts to use the result of that change.

If Transaction B depends on the state created by Transaction A, the order of execution matters. The first transaction must be processed before the second one can produce the intended result. In account-based systems such as Ethereum, transactions from the same account also follow nonce ordering rules. A later transaction cannot simply be processed as though an earlier transaction from that account had already been completed. Smart contracts introduce additional complexity. Two transactions interacting with the same contract may produce different results depending on which one executes first. For example, imagine a decentralised exchange where two users submit transactions to exchange tokens. If the first transaction changes the available liquidity or the price, the second transaction may execute under different conditions. This means transaction ordering is not merely a question of presentation. It can directly affect the resulting state of the blockchain.

5.5 Ordering in Bitcoin

Bitcoin uses a UTXO-based transaction model. A transaction spends existing unspent transaction outputs and creates new outputs. If one transaction creates an output that another transaction spends, the creating transaction must appear first in the valid sequence. This is a dependency between transactions. Miners must respect such dependencies when constructing a block. For example:

  • Transaction A creates a new UTXO.
  • Transaction B spends that UTXO.
  • Transaction B cannot be validly processed before Transaction A.

Bitcoin's block structure records transactions in a specific order. The first transaction in a block is the coinbase transaction, which creates the block subsidy and collects the transaction fees according to the protocol rules. The remaining transactions are arranged by the miner or mining pool, subject to validity and dependency constraints. Bitcoin does not require all transactions to be arranged by a single universal fee-ranking algorithm. Different miners can construct different valid candidate blocks from the transactions available to them.

5.6 Ordering in Ethereum

Ethereum uses an account-based model and an execution environment designed to process transactions and update the network's state. The selected transactions are placed into an execution payload in a defined order. The execution client processes them sequentially. Each transaction can change the state that subsequent transactions will encounter. This is especially important for smart contracts and decentralised applications. Ethereum block construction can involve more than one specialised role. A validator selected to propose a block may construct the execution payload itself or obtain a payload prepared by an external block builder through infrastructure such as MEV-Boost. This separation of block building and block proposing is commonly discussed under the term Proposer-Builder Separation (PBS). The distinction is important:

  • A builder can specialise in selecting and ordering transactions.
  • A proposer is responsible for proposing the block within the consensus protocol.
  • Other validators check the proposed block and its execution results.

External builder infrastructure is not the same thing as a fully protocol-native separation of these roles. Ethereum's proposer-builder architecture continues to develop through protocol research and upgrades. Transaction ordering also creates economic opportunities and risks, particularly in decentralised finance. The order in which trades, liquidations and other contract operations execute can influence the value received by participants.

5.7 Ordering in Cardano

Cardano uses an extended UTXO model, known as eUTXO. Transactions consume existing outputs and create new ones. They can also interact with scripts that determine whether particular spending conditions are satisfied. The relationship between inputs and outputs creates dependencies that must be respected when transactions are processed. Cardano's block producer must construct a block containing transactions that are valid under the ledger rules and fit within the applicable protocol limits. The transaction sequence matters because each accepted transaction can change the ledger state available to subsequent transactions. This is one reason why Cardano's approach to transaction processing differs from Ethereum's account-based execution model. The two networks may both process transactions that interact with decentralised applications, but their underlying ledger models impose different constraints on transaction construction and ordering.

5.8 Block Production Is Not the Same as Consensus

A particularly important distinction is the difference between producing a block and reaching consensus about the blockchain's history. A block producer creates a candidate block and broadcasts it to other participants. Other nodes and validators independently check whether the block follows the protocol rules. They also determine how it fits into the chain according to the network's consensus and fork-choice rules. This distinction matters because two different participants may sometimes produce competing blocks that extend the same previous block. For example, two Bitcoin miners may find valid Proof-of-Work solutions at nearly the same time. Some nodes may receive one block first, while other nodes receive the competing block first. The network can temporarily have different views of the chain. Bitcoin's Proof-of-Work consensus eventually resolves this situation as additional work is added to one branch and nodes update their preferred chain. In Ethereum, validators use the network's fork-choice mechanism and attestations to determine which chain to follow. Cardano's Ouroboros protocol also defines how participants assess competing blocks and select the chain. The general principle is that block production creates a proposal; consensus determines how that proposal fits into the accepted history.

5.9 Why Can Different Valid Blocks Contain Different Transactions?

Block producers do not necessarily share identical mempools or transaction-selection strategies. Even when they follow the same protocol, they may construct different candidate blocks. Imagine two miners:

  • Miner A knows about transactions 1, 2, 3 and 4.
  • Miner B knows about transactions 1, 2, 3, 4 and 5.

They may also choose different transaction orders or apply different selection strategies. Both can produce valid candidate blocks, provided their blocks satisfy the consensus and transaction rules. This is one reason why independent block producers can construct different blocks without violating the protocol. The network does not require every miner or validator to prepare an identical candidate block in advance. Instead, the protocol defines the conditions that a valid block must satisfy and the rules used to determine the accepted chain.

5.10 Transaction Ordering, MEV and Fairness

Transaction ordering can have economic consequences. In Ethereum and other smart-contract environments, the term Maximal Extractable Value (MEV) describes value that can be obtained by influencing which transactions are included in a block and in what order. For example, a block builder may identify an opportunity involving several transactions in a decentralised exchange. By placing transactions in a particular sequence, the builder may obtain additional revenue or affect the execution price experienced by other users. MEV can arise from several activities:

  • Arbitrage between different markets.
  • Liquidations of under-collateralised positions.
  • Transactions placed before or after another transaction.
  • Other strategies that depend on the ordering of operations.

Not all MEV is necessarily harmful. Some activities, such as arbitrage, can help align prices across markets. However, transaction-ordering opportunities can also create unfair advantages, increase costs for users or encourage centralisation among specialised block builders. This is why transaction ordering is not only a technical design question. It is also an economic and governance concern.

5.11 What Happens After a Block Is Produced?

Once a candidate block has been assembled, it is broadcast to other network participants. Nodes verify the block according to the rules of the relevant blockchain. These checks include the block's structure, its relationship to the previous block, the validity of its transactions and the correctness of the resulting ledger state. If the block passes the required checks, participants can incorporate it into their local view of the chain. The consensus protocol then coordinates the network's treatment of that block. Depending on the blockchain, the block may become increasingly secure as additional blocks or validator attestations accumulate, or it may reach a protocol-defined finality state. This brings us back to the distinction established in the previous sections:

  • A transaction is not a block.
  • A candidate block is not necessarily an accepted block.
  • Block production is not the same as consensus.
  • Inclusion in a block is not always equivalent to finality.

Each process performs a different function within the architecture of a blockchain system.

5.12 Why Block Production and Ordering Matter

Block production is the mechanism through which pending transactions become organised units of blockchain history. Transaction ordering determines the sequence in which operations are processed and can influence the resulting state of the network. Understanding these processes helps explain:

  • Why miners and validators have different responsibilities.
  • Why block producers can select different transactions.
  • Why transaction order can affect smart-contract results.
  • Why competing blocks can temporarily exist.
  • Why consensus is necessary after block production.
  • Why transaction ordering can create economic incentives and risks.

The block is therefore not simply a technical container. It is a carefully structured proposal that connects transaction execution, data organisation and network consensus.

Research Note

Block production transforms selected pending transactions into a candidate block. The process is governed by network-specific rules concerning producer selection, transaction validity, resource limits, dependencies and ordering. Bitcoin miners construct candidate blocks through Proof of Work. Ethereum validators propose blocks within a Proof-of-Stake architecture, while specialised builders may participate in preparing execution payloads. Cardano stake pool operators produce blocks under the Ouroboros protocol. Transaction ordering can influence the resulting ledger state, particularly in networks with smart-contract execution. The production of a block must therefore be distinguished from the consensus process that determines which blocks become part of the accepted chain.

06. Data Structures And Merkle Trees

How blockchain systems organise transaction data, connect blocks through cryptographic hashes and make information independently verifiable.

6.1 Why Do Blockchains Need Data Structures?

A blockchain network processes a continuous stream of transactions. These transactions must be organised, stored and connected in a way that allows independent participants to verify the network's history. Simply collecting transactions in a long list would not provide all the properties required by a distributed ledger. A blockchain needs structures that can:

  • Organise transactions into blocks.
  • Connect each block to its predecessor.
  • Represent transaction data through cryptographic commitments.
  • Support efficient verification of individual records.
  • Allow participants to detect changes to previously recorded information.
  • Represent the network's current ledger state.

Different blockchain systems use different data structures to achieve these goals. Bitcoin, Ethereum and Cardano provide useful examples of three different approaches to organising distributed data. Before examining them, we need to understand two fundamental concepts: cryptographic hashes and Merkle structures.

6.2 Cryptographic Hashes as Digital Fingerprints

A cryptographic hash function takes an input of arbitrary length and produces an output of a fixed length. The output is commonly called a hash or hash value. For example, a hash function can process:

  • A short text message.
  • A digital document.
  • A transaction.
  • A block of data.
  • A collection of other hashes.

Regardless of the input's size, the function produces an output with a defined length. A useful property of a cryptographic hash function is that even a small change in the input should produce a substantially different output. Imagine that a document contains the following sentence: The network recorded 100 transactions. Now imagine changing the number to 101. The resulting hash will be different. A participant comparing the two hashes can detect that the underlying data has changed. Cryptographic hashes are therefore useful for identifying data and checking its integrity. However, a hash is not an encryption method. It does not hide the original information or provide a way to recover it. It is a one-way cryptographic transformation designed to make verification possible without revealing the original input through the hash itself. Bitcoin uses the double SHA-256 hash function for several important structures, including its block headers and transaction identifiers. Ethereum uses Keccak-256 in its execution-layer data structures. Cardano uses cryptographic hash functions including Blake2b in different parts of its architecture. The exact algorithms and their applications depend on the protocol.

6.3 How Blocks Are Connected

A blockchain is organised as a sequence of blocks. Each block contains information that connects it to a previous block. In Bitcoin, the block header includes the hash of the preceding block's header. This creates a cryptographic link:

  • Block 100 contains the hash of Block 99.
  • Block 101 contains the hash of Block 100.
  • Block 102 contains the hash of Block 101.

The sequence continues as new blocks are accepted. Simplified illustration of the relationship between consecutive blocks.

Each block commits to the hash of its predecessor. This illustration simplifies the actual block-header structure. If someone changes the contents of an earlier block, its hash changes. The next block still contains the old hash, so the connection no longer matches. The same problem continues through subsequent blocks because each one depends on the hash of its predecessor. This is one of the mechanisms that makes historical modification detectable. It does not mean that changing historical data is physically impossible. Rather, changing an accepted history requires overcoming the network's consensus and security mechanisms. The connection between blocks is one of the defining structural properties of a blockchain.

6.4 What Is a Merkle Tree?

A Merkle tree is a data structure that organises information through successive levels of cryptographic hashes. It allows a large collection of data to be represented by one final hash called the Merkle root. The basic process works as follows:

  1. Each transaction is represented by its transaction hash.
  2. The hashes are arranged as the first level, called the leaves.
  3. Pairs of hashes are combined and hashed together.
  4. The resulting hashes form the next level.
  5. The process continues until only one hash remains.

That final hash is the Merkle root. Simplified example with four transactions.

The important point is that the Merkle root represents the entire collection of transactions through a single cryptographic commitment. If one transaction changes, its hash changes. That change propagates through the levels of the tree and produces a different root. This makes it possible to detect modifications without comparing every transaction individually.

6.5 How Does a Merkle Proof Work?

One of the most useful properties of a Merkle tree is that it can support efficient verification of an individual transaction. Imagine that a block contains thousands of transactions, but a participant wants to check only whether one particular transaction is included. The participant does not necessarily need to download the entire block. Instead, a full node or another information provider can supply:

  • The transaction being checked.
  • Its position in the block.
  • The necessary neighbouring hashes along the path to the Merkle root.
  • The block header containing the Merkle root.

The participant combines the transaction hash with the supplied hashes, following the correct order and hashing rules. If the calculation produces the Merkle root recorded in the block header, the participant has verified that the transaction belongs to the committed transaction set. This information is called a Merkle proof or Merkle branch. The amount of proof data grows logarithmically with the number of transactions rather than requiring the complete transaction list. For a binary Merkle tree containing approximately one million transactions, a proof would require roughly twenty sibling hashes, rather than one million transaction records. This makes Merkle proofs useful for lightweight verification systems. There is an important limitation, however. A Merkle proof establishes that a particular transaction is included in the data committed to by a block header. By itself, it does not prove that the transaction is valid under every consensus rule or that the block has reached finality. Those questions require additional verification.

6.6 Bitcoin: Merkle Trees and the Block Header

Bitcoin uses a binary Merkle tree to summarise the transactions included in a block. Each transaction is represented by its transaction identifier (TXID). The TXIDs are arranged in their original block order and combined in pairs. Bitcoin uses double SHA-256 hashing to calculate the intermediate nodes and the final Merkle root. If a level contains an odd number of hashes, the final hash is duplicated to create a pair. The resulting Merkle root is included in the Bitcoin block header. Bitcoin's block header contains six principal fields:

  • Version.
  • Previous block header hash.
  • Merkle root.
  • Timestamp.
  • Difficulty target, represented by the nBits field.
  • Nonce.

Together, these fields form the 80-byte Bitcoin block header. The header is particularly important because miners perform Proof-of-Work calculations on its hash. Changing a transaction changes the Merkle root, which changes the block header hash. This means the block's original Proof-of-Work result no longer corresponds to the modified header. Bitcoin also uses a separate witness commitment mechanism for Segregated Witness data. The ordinary transaction Merkle root is based on TXIDs, while witness data is committed through an additional structure involving the coinbase transaction. This distinction is important because not all transaction data is represented by the ordinary TXID Merkle tree.

Simplified Payment Verification

Merkle proofs are especially useful for lightweight Bitcoin clients. A lightweight client does not need to store and independently validate every transaction in the entire blockchain. It can request block headers and a Merkle proof from a full node, then verify that the transaction is included in the block represented by the header. This approach is known as Simplified Payment Verification (SPV). However, SPV is not equivalent to full-node validation. It provides evidence of transaction inclusion in a block whose header belongs to the relevant Proof-of-Work chain. It does not independently verify every transaction or all consensus rules in the way a fully validating node does.

6.7 Ethereum: Merkle Patricia Tries

Ethereum uses a more complex data structure known as the Merkle Patricia Trie (MPT). It combines properties of Merkle trees and Patricia tries. A traditional binary Merkle tree combines pairs of hashes. A Patricia trie organises key-value information according to paths derived from keys. Ethereum combines these ideas to support efficient data organisation, retrieval and cryptographic verification. The execution layer uses three particularly important trie structures:

State Trie

The state trie represents the global state of Ethereum, including account information and references to contract storage. Its root is called stateRoot.

Transactions Trie

The transactions trie represents the transactions included in a particular block, preserving their original order. Its root is called transactionsRoot.

Receipts Trie

The receipts trie stores transaction receipts, which contain information about transaction execution results and related data. Its root is called receiptsRoot. These three roots are included in the execution block header. They serve as cryptographic commitments to different parts of the network's data. This means Ethereum's data architecture is more extensive than simply placing a binary Merkle root over a list of transactions. It uses several related structures to represent transactions, execution results, account state and contract storage.

6.8 Why Does Ethereum Need More Than One Root?

Ethereum is not only a system for recording transfers between accounts. It also executes smart contracts and maintains a changing global state. For this reason, the network must commit to more than the list of transactions included in a block. Consider a simplified example. A user submits a transaction that calls a smart contract. The transaction may change:

  • The user's account balance.
  • The contract's stored variables.
  • Token balances.
  • Other application data.
  • Information recorded in transaction logs.

The transactions root commits to the transactions themselves. The receipts root commits to the corresponding execution receipts. The state root commits to the resulting global state after the block's transactions have been processed. These roots provide different forms of information and should not be treated as interchangeable. They allow Ethereum clients and other verification systems to check different aspects of the network's data.

6.9 Cardano: Block Structure and Cryptographic Commitments

Cardano also uses cryptographic data structures to organise and verify its ledger. A Cardano block contains a header and a body. The header contains information needed to identify the block, connect it to the preceding chain and verify important properties of the block body. The body contains the transactions and associated data. Cardano uses cryptographic hashes and structured commitments to connect block information with its contents. Its design must be understood in the context of the extended UTXO model and the Ouroboros consensus protocol. Cardano's data structures are not simply identical to Bitcoin's binary Merkle tree or Ethereum's Merkle Patricia Trie. The networks use different transaction models, block formats and verification mechanisms. Merkle-based structures are useful for understanding the general principle of cryptographic commitments, but a detailed description of Cardano must follow its own block and ledger specifications. The important architectural idea is that the block header provides a compact cryptographic representation of important block information, allowing participants to verify relationships between the header and the block's contents.

6.10 What Happens If Data Is Changed?

Cryptographic data structures make unauthorised modifications detectable. Consider a simplified Bitcoin example. A block contains four transactions. Their hashes are combined into a Merkle tree, and the final Merkle root is stored in the block header. Now imagine changing one transaction. The sequence is:

  1. The modified transaction produces a different transaction hash.
  2. The affected intermediate hash changes.
  3. The next level of the tree changes.
  4. The Merkle root changes.
  5. The block header changes.
  6. The block header hash changes.
  7. The next block's previous-block reference no longer matches the modified block.

This demonstrates how cryptographic commitments and block linking work together. In Ethereum, changing a transaction or the resulting state also affects the relevant trie roots and therefore the execution block's commitments. These structures do not make alteration physically impossible. They make unauthorised changes detectable and force an attacker to overcome the relevant consensus and security mechanisms if they want the modified history to be accepted.

6.11 Data Integrity Is Not the Same as Data Availability

A cryptographic commitment can prove that information matches a previously established hash. However, it does not automatically guarantee that the underlying information is available to everyone who needs it. For example, a block header may contain a valid Merkle root, but a lightweight client still needs access to the relevant transaction and proof data to verify a particular inclusion claim. This distinction is important:

  • Data integrity concerns whether information has been altered.
  • Data availability concerns whether the information can actually be obtained.
  • Data validity concerns whether the information follows the protocol rules.
  • Consensus concerns how the network agrees on the accepted chain or state.

These are related but separate properties. A blockchain's security depends on how its architecture addresses all of them.

6.12 Why Data Structures and Merkle Trees Matter

Data structures determine how blockchain systems organise, connect and verify information. Cryptographic hashes provide compact digital fingerprints. Block headers connect successive blocks. Merkle trees and related structures allow large collections of data to be represented through cryptographic commitments. Understanding these mechanisms helps explain:

  • Why changing transaction data changes cryptographic commitments.
  • How blocks are linked to earlier blocks.
  • How a Merkle proof can establish transaction inclusion.
  • Why lightweight clients can verify selected information without storing the entire chain.
  • Why Ethereum maintains separate roots for state, transactions and receipts.
  • Why different blockchains require different data structures.

The central idea is that blockchain architecture does not rely only on storing information. It also defines how information can be connected, verified and independently checked by participants.

07. Execution Layer

How blockchain systems process transactions, execute programmable instructions and calculate changes to the distributed ledger.

7.1 What Is the Execution Layer?

A blockchain does more than receive transactions and record them in blocks. It must also determine what each transaction actually does. A transaction may transfer digital assets, create a new token, interact with a smart contract or change information stored in a decentralised application. The network needs a mechanism to process these instructions according to its protocol rules. This function is commonly associated with the execution layer. The execution layer is responsible for processing transactions and calculating their effects on the blockchain's ledger state. Depending on the network, it may include:

  • Transaction execution and validation.
  • Interpretation of programmable instructions.
  • Smart-contract execution.
  • Calculation of transaction fees and resource consumption.
  • Updates to account balances, UTXOs or contract storage.
  • Calculation of the resulting ledger state.

Not every blockchain implements execution as a separate architectural layer. Ethereum has a clearly defined execution layer that works alongside its consensus layer. Bitcoin uses a more limited scripting and transaction-validation model. Cardano integrates smart-contract script execution into its ledger validation process. These differences are important because the term execution layer describes a function, not one universal technical design.

7.2 Execution and State Transitions

To understand execution, we first need to understand the concept of state. A blockchain's state represents the information that determines the current condition of its ledger. Depending on the network, this information may include:

  • Account balances.
  • Unspent transaction outputs.
  • Smart-contract storage.
  • Token ownership.
  • Other protocol-defined records.

A transaction can change this state. Imagine that Alice sends 2 units of a digital asset to Bob. Before the transaction:

  • Alice controls the funds.
  • Bob does not yet control the transferred amount.

After a valid transaction is processed:

  • Alice's available funds are reduced.
  • Bob's available funds are increased.
  • The ledger reflects the new ownership arrangement.

This transformation is called a state transition. In a simplified mathematical representation:

[

S' = F(S,T)

]

Where:

  • (S) is the previous state.
  • (T) is the transaction or set of transactions.
  • (F) represents the protocol's execution and validation rules.
  • (S') is the resulting state.

The same valid input, processed under the same protocol rules and starting state, must produce the same result. This predictability is essential. Independent nodes must be able to calculate and verify the same outcome. The exact state-transition model differs between blockchain architectures.

7.3 The Ethereum Virtual Machine (EVM)

Ethereum provides one of the clearest examples of a programmable execution environment. Its execution environment is called the Ethereum Virtual Machine (EVM). The EVM is a virtual machine: a software-defined environment that processes instructions according to a specified set of rules. It allows developers to create smart contracts that can perform operations when called by transactions. A smart contract is not a traditional legal contract in the everyday sense. It is a program stored and executed according to the rules of the blockchain. For example, a smart contract can implement:

  • Token transfers.
  • Decentralised exchange operations.
  • Lending and borrowing mechanisms.
  • Voting systems.
  • Digital asset ownership rules.
  • Automated application logic.

When a transaction calls a smart contract, the EVM processes the contract's instructions. The execution can read and modify the state available to the contract, subject to the protocol rules. The result is calculated by the execution client and can be independently reproduced by other correctly operating Ethereum clients. This is how Ethereum turns programmable instructions into changes to its shared ledger.

7.4 How Does the EVM Execute Instructions?

Smart contracts are generally written in higher-level programming languages such as Solidity or Vyper. Before deployment, their code is compiled into EVM bytecode. Bytecode is a lower-level representation of instructions that the EVM can execute. The EVM processes these instructions using a stack-based execution model. Its instruction set includes operations for:

  • Arithmetic.
  • Comparisons.
  • Reading and writing storage.
  • Working with memory.
  • Calling other contracts.
  • Checking transaction and block information.
  • Controlling program execution.

The EVM also maintains different forms of data during execution.

Stack

A temporary structure used to hold values required by instructions.

Memory

Temporary working space available during a transaction's execution. Its contents do not persist as permanent contract storage.

Storage

Persistent key-value data associated with a smart contract. Changes to storage can become part of the blockchain's resulting state.

Calldata

The input data supplied to a contract call. It commonly contains the function identifier and encoded arguments. These components serve different purposes. For example, a smart contract may receive a request to transfer tokens. The EVM reads the supplied arguments, checks the relevant conditions, performs calculations and updates the contract's persistent storage if the operation succeeds. The resulting state changes are then represented in the execution results of the transaction.

7.5 Gas: Measuring Computational Resources

Executing instructions requires resources. A blockchain cannot allow participants to submit unlimited computation without considering the costs imposed on the network. Ethereum addresses this problem through a mechanism called gas. Gas measures the computational resources required to execute transactions and EVM instructions. Different operations consume different amounts of gas. For example:

  • Basic arithmetic requires relatively little computation.
  • Reading or modifying persistent storage can require more resources.
  • Calling other contracts can involve additional execution.
  • Complex operations may consume substantially more gas.

Each transaction has a gas limit that restricts the amount of gas it can consume. If execution requires more gas than the transaction allows, the transaction can run out of gas and fail. The transaction is still included in the block if it was validly processed under the protocol rules, but its intended execution changes are reverted. The sender still pays for the gas consumed. Gas serves several purposes:

  1. It measures computational work.
  2. It limits the resources a transaction can consume.
  3. It helps protect the network against uncontrolled computation.
  4. It provides an economic mechanism for allocating scarce block resources.

Gas is not simply another name for ETH. Gas measures computational work, while ETH is the asset used to pay transaction fees. The fee calculation depends on the applicable gas price and the amount of gas consumed.

7.6 What Happens When a Smart Contract Executes?

Consider a simplified decentralised exchange. A user wants to exchange one token for another. The user submits a transaction calling the exchange's smart contract. The EVM processes the instructions and checks the conditions required for the operation. The contract may need to:

  1. Identify the tokens involved.
  2. Read the relevant liquidity information.
  3. Calculate the expected exchange amount.
  4. Check the user's available balance and permissions.
  5. Apply the exchange rules.
  6. Update the contract's stored information.
  7. Record the resulting token transfers.

If all required conditions are satisfied, the transaction can complete successfully. If a required condition is not satisfied, the execution may revert. For example, the user may have specified a minimum amount of tokens to receive. If the calculated amount falls below that limit, the contract can reject the intended operation. This illustrates why smart-contract execution is more than recording a transfer. The blockchain processes a program whose instructions determine whether and how the requested operation changes the ledger.

7.7 Bitcoin: A More Limited Execution Model

Bitcoin also processes programmable conditions, but its architecture differs substantially from Ethereum. Bitcoin uses a scripting system called Bitcoin Script. It is a deliberately restricted, stack-based scripting language used primarily to define and verify the conditions under which transaction outputs can be spent. For example, a Bitcoin output may require:

  • A valid digital signature.
  • A particular public key.
  • Several signatures from a group of participants.
  • Satisfaction of specified time or sequence conditions.
  • Other conditions supported by the scripting system.

When someone attempts to spend the output, the relevant scripts are evaluated. If the required conditions are satisfied, the spending transaction can pass this part of validation. If they are not satisfied, the transaction is invalid. Bitcoin Script is intentionally not a general-purpose, Turing-complete smart-contract environment like the EVM. Its restricted design limits computational complexity and makes transaction-spending conditions more predictable. This does not mean that Bitcoin has no programmable functionality. It means that Bitcoin's scripting model is designed for a narrower purpose: defining and verifying conditions for spending transaction outputs. Modern Bitcoin also supports more advanced spending constructions through upgrades such as SegWit and Taproot. However, its execution model remains fundamentally different from Ethereum's general-purpose smart-contract environment.

7.8 Cardano: Script Execution Within the Ledger

Cardano follows another architectural approach. It uses an extended UTXO model, known as eUTXO, and supports programmable validation through Plutus scripts. In Cardano, a transaction consumes existing UTXOs and creates new outputs. Some outputs are protected by validator scripts rather than relying only on a conventional public-key signature. When a transaction attempts to spend a script-locked output, the relevant script is evaluated during transaction validation. The script receives the information required by the validation rules, including:

  • The datum associated with the output, where applicable.
  • The redeemer supplied by the transaction.
  • The transaction context.

The script determines whether the proposed spending operation satisfies the required conditions. Cardano's scripting system is based on Plutus Core, a functional programming language. Developers can use higher-level tools and languages to create smart contracts that are compiled into the form executed by the ledger. An important characteristic of Cardano's design is that script validation is closely connected to its eUTXO ledger model. Transactions specify the inputs they consume and the outputs they create. This allows many transaction outcomes to be evaluated locally before submission. However, a transaction can still fail if another transaction consumes one of its required inputs before it is included in a block. Cardano also defines execution budgets for scripts, measured in computational steps and memory units. These limits help prevent transactions from consuming unbounded network resources.

7.10 Deterministic Execution

A blockchain needs independent participants to obtain consistent results. If two correctly operating nodes start with the same valid state and process the same valid block under the same protocol rules, they must calculate the same resulting state. This property is known as deterministic execution. Consider what would happen if two nodes processed the same transaction but obtained different results. One node might record a token transfer, while another might reject it. The network would no longer have a consistent ledger state. To avoid this, blockchain execution environments define precise rules for:

  • Instruction processing.
  • Data representation.
  • Transaction validation.
  • Resource consumption.
  • State updates.
  • Error handling.

Ethereum's EVM is designed to provide deterministic execution. Cardano's Plutus validation model also emphasises predictable results for a given transaction and its specified inputs. Bitcoin's restricted scripting system provides a comparatively narrow and predictable way to evaluate spending conditions. Determinism is therefore a fundamental requirement of blockchain execution, although different architectures achieve it through different mechanisms.

7.11 Execution Failure and Transaction Reversion

Not every transaction that reaches an execution environment completes its intended operation. A transaction may fail because:

  • A smart contract rejects the requested operation.
  • A required condition is not satisfied.
  • The transaction exceeds its permitted computational resources.
  • A script evaluates to an invalid result.
  • The transaction depends on state that has changed.
  • A protocol rule is violated.

The consequences of failure depend on the blockchain. In Ethereum, a transaction that fails during EVM execution can still be included in a block. Its intended state changes are reverted, while the sender pays for the computational resources already consumed. In Bitcoin, a transaction that fails the required script or consensus validation cannot be accepted as a valid transaction in a block. In Cardano, a transaction whose required validation scripts fail is not applied as an ordinary successful ledger transition. Cardano also defines collateral mechanisms for certain script-related failures, so the consequences for the transaction's collateral must be distinguished from a successful execution. These differences are important when comparing transaction costs and smart-contract behaviour. A failed transaction does not necessarily mean that no resources were consumed.

7.12 Execution Layer and Consensus Layer

The execution layer and consensus layer perform different functions. The execution layer processes transactions and calculates their effects on the ledger. The consensus layer coordinates the network's agreement on blocks and the accepted chain. In Ethereum, this separation is particularly clear. The execution layer handles transactions, smart contracts and state transitions. The consensus layer coordinates validators, block proposals, attestations, fork choice and finality. These layers communicate with one another, but they do not perform the same task. Bitcoin and Cardano organise their responsibilities differently, and their architectures should not be forced into Ethereum's exact terminology. The distinction is nevertheless useful when studying blockchain systems:

  • Execution determines the result of operations under the protocol rules.
  • Consensus coordinates agreement on the accepted history.
  • Data structures represent the information and state.
  • Networking allows independent participants to exchange information.

Together, these functions allow a distributed blockchain system to process transactions without relying on one central computer to maintain the authoritative ledger.

7.13 Why the Execution Layer Matters

The execution environment determines what a blockchain can do beyond simply recording transfers. It influences:

  • Which applications can be built on the network.
  • How smart contracts are written and executed.
  • How transaction costs are calculated.
  • How computational resources are limited.
  • How ledger state changes.
  • How predictable transaction outcomes are.
  • What security risks developers and users must consider.

Ethereum's EVM supports a broad range of programmable applications. Bitcoin Script focuses on controlled spending conditions. Cardano integrates programmable validation into its extended UTXO ledger. These are different architectural choices, each with its own advantages, constraints and trade-offs. Understanding the execution layer is essential for understanding why blockchain networks that may appear similar at first can support very different types of applications.

08. State, Storage And State Transitions

8.1 What Is State in a Blockchain?

A blockchain does not simply record a sequence of transactions. It must also maintain a consistent representation of the system after those transactions have been processed. This representation is called the state. State describes the information that is currently relevant to the operation of the network. Depending on the blockchain's architecture, it may include:

  • Which transaction outputs remain unspent.
  • The balances and nonces associated with accounts.
  • Smart contract code and persistent storage.
  • Data required to determine whether future transactions are valid.
  • Other protocol-defined information needed to process new blocks.

State is not identical to the complete transaction history. The transaction history records what happened. The current state represents the result of applying the accepted transactions according to the protocol rules. For example, a transaction may transfer value from one participant to another. The transaction remains part of the historical record, while the current state reflects the new ownership arrangement. This distinction is fundamental to understanding blockchain architecture.

8.2 State as the Result of State Transitions

A blockchain changes its state through a defined process called a state transition. A simplified model can be expressed as:

[

S_{new}=F(S_{previous},T)

]

Where:

  • (S_{previous}) is the state before a transaction.
  • (T) is the transaction being processed.
  • (F) represents the protocol's validation and transition rules.
  • (S_{new}) is the resulting state.

At the block level, the same principle applies to an ordered collection of transactions. Each transaction is processed according to the state produced by the preceding transaction. Therefore, transaction order can affect the final result. A transaction cannot simply declare that an account owns a certain amount or that a particular output is available. The network checks whether the proposed change follows the rules of its ledger. In a correctly functioning blockchain, nodes independently verify the validity of state transitions rather than accepting an unverified claim about the new state. The transition rules must be deterministic: given the same valid starting state and the same transaction data, compliant nodes must calculate the same result. This shared calculation is essential for maintaining consistency across a distributed network.

8.3 Bitcoin: State as the UTXO Set

Bitcoin uses the Unspent Transaction Output (UTXO) model. Instead of maintaining an account balance for every address, Bitcoin tracks individual transaction outputs that have been created and have not yet been spent. The collection of these outputs at a particular point in the chain is called the UTXO set. Each UTXO represents a specific amount of bitcoin associated with conditions that determine how it may be spent. A transaction consumes existing UTXOs and creates new outputs. For example, imagine that Alice controls two unspent outputs:

  • UTXO A: 0.7 BTC
  • UTXO B: 0.5 BTC

She wants to send Bob 0.9 BTC. Her transaction may consume both outputs and create:

  • 0.9 BTC for Bob.
  • 0.299 BTC as change for Alice.
  • 0.001 BTC as a transaction fee.

The original UTXOs are consumed. The newly created outputs become part of the updated UTXO set once the transaction is accepted into the chain. The important point is that a UTXO is spent as a whole. If its full value is not needed for a payment, the transaction can create a separate change output. Bitcoin does not maintain a simple account balance for each wallet address at the protocol level. Wallet software calculates a displayed balance by identifying and summing the relevant unspent outputs. This means that a wallet balance is a convenient representation of several underlying UTXOs, not necessarily one individual record. The UTXO model also provides a clear way to prevent double spending: once an output has been spent in the accepted chain, it cannot be spent again.

8.4 Ethereum: State as a Global Account-Based System

Ethereum uses an account-based model. Its execution state contains information about accounts, including externally owned accounts and smart contract accounts. Each account has four principal fields:

  • Nonce — a counter used to track transactions or contract creation.
  • Balance — the amount of ETH associated with the account.
  • Storage root — a cryptographic commitment to the account's persistent storage.
  • Code hash — a hash identifying the account's associated contract code.

An externally owned account is controlled by private keys. A contract account is controlled by its programmed logic. Unlike Bitcoin's UTXO model, Ethereum updates account-based state as transactions are executed. For example, when Alice sends ETH to Bob, the execution process updates the relevant account balances. When a smart contract changes its internal data, the corresponding storage values are updated as well. This does not mean that the entire history is rewritten. The historical transactions remain recorded, while the current account state reflects their accepted effects. Ethereum organises execution state using a global state structure based on a Merkle Patricia Trie. Each account's storage is represented separately, with its own storage trie. The account's storageRoot commits to that storage structure. This architecture allows the network to represent a large amount of account and contract information while maintaining cryptographic commitments to the resulting state.

8.5 Cardano: State Through the Extended UTXO Model

Cardano uses an Extended UTXO (eUTXO) model. It retains the basic UTXO approach used by Bitcoin but extends transaction outputs with additional information that supports more expressive smart contracts. A Cardano transaction output can contain:

  • An address.
  • A value, including ADA and native assets.
  • An optional datum or datum hash.
  • Conditions associated with the address and its spending rules.

The datum can hold structured information associated with a particular output. It can therefore represent part of a smart contract's state. A redeemer supplies information about the action a transaction is attempting to perform. The validator evaluates the datum, redeemer and transaction context to determine whether spending is permitted. A useful distinction is that Cardano does not update a persistent contract variable in the same way as an account-based system. Instead, a transaction can consume an existing script-locked UTXO and create a new output containing updated state information. For example, imagine a smart contract that tracks the status of a shared project. Its current state might be represented by a UTXO containing a datum that records:

  • The current project stage.
  • The amount of funds available.
  • The conditions required for the next stage.

When a valid transaction advances the project, it consumes the previous UTXO and creates a new one with updated information. The validator checks whether the proposed transition follows the contract's rules. This approach makes the state transition explicit: the previous state is consumed, and a new state is represented by newly created outputs. If another transaction spends the same input first, a competing transaction that depends on that input can no longer use it. This is an important practical consideration when designing applications on eUTXO networks.

Bitcoin, Ethereum and Cardano all maintain a state that allows nodes to determine which transactions are valid. However, the way each network represents that state differs significantly.

8.7 Historical Data and Current State

A blockchain's historical record and its current state serve different purposes. The historical record contains the accepted sequence of blocks and transactions. The current state represents the result of processing that history according to the protocol rules. Consider a Bitcoin transaction that creates an output worth 0.5 BTC. Later, another transaction spends that output. The original transaction remains part of the blockchain history. However, its output is no longer part of the current UTXO set. The same general distinction exists in account-based systems. An Ethereum transaction may change an account's balance or a contract's storage. The earlier transaction remains recorded, but the current state contains the updated values. This distinction matters because knowing the current state does not necessarily provide every detail about the past. A node or application may need historical data to investigate an earlier balance, reconstruct a previous contract value or analyse how the network reached its present condition. Different node configurations and data services may retain or expose different amounts of historical information. For example, an archive-capable service can provide access to historical state information that may not be readily available from a node retaining only the data needed for its current operation. It is therefore important to distinguish:

  • Blockchain history — the recorded sequence of accepted blocks and transactions.
  • Current state — the result of applying those records.
  • Historical state — the state that existed at an earlier point in the chain.

These are related, but they are not interchangeable.

8.8 State Storage and Node Responsibilities

A blockchain node must maintain enough information to perform its assigned role. For a full node, this generally includes the ability to validate new blocks and transactions against the relevant protocol rules. The internal storage architecture depends on the blockchain implementation. A node may maintain:

  • Block data.
  • Transaction indexes or other supporting indexes.
  • Current ledger or execution state.
  • Information required for validation.
  • Additional historical data, depending on its configuration.

The distinction between storing the complete history and maintaining the current state is especially important. For example, Bitcoin nodes use the UTXO set to determine whether transaction inputs refer to outputs that remain unspent. Ethereum execution clients maintain execution state, including account and contract information, so that transactions can be processed and their effects checked. Cardano nodes maintain ledger information needed to validate transactions and track the current UTXO state. A wallet or blockchain explorer may display a simplified view of this information. However, such an interface is not the same thing as the underlying ledger. The displayed balance, token list or transaction history is produced by software that reads and interprets blockchain data. This is one reason why different applications can present information differently even when they refer to the same network.

8.9 State Roots and Cryptographic Commitments

How can a distributed network check that nodes have arrived at the same state? One important mechanism is the use of cryptographic commitments. A state commitment is a compact cryptographic representation of a larger data structure. It allows a node to verify that a particular state corresponds to a specified root value without placing the entire state into a block header. Ethereum uses a stateRoot in its execution block structure. After processing the transactions in a proposed block, execution clients calculate the resulting state. Other clients independently process the same transactions and check whether their result matches the state commitment included in the block. If the calculated state does not match the expected commitment, the block fails the relevant validity checks. This provides an important link between transaction execution, state storage and block validation. However, the details differ among blockchain systems. Ethereum's execution state root is not the same thing as Bitcoin's UTXO set. Bitcoin's ordinary block header does not contain a direct commitment to the complete current UTXO set in the same way. This distinction matters: cryptographic data structures may serve related purposes across different networks, but their placement and protocol roles are not necessarily identical. A state commitment also does not independently prove that every underlying transaction was valid. The network must still apply the appropriate validation and consensus rules.

8.10 State Consistency and Independent Verification

A distributed blockchain requires participating nodes to maintain a consistent view of the accepted ledger. This does not mean that every node must store every possible piece of information in exactly the same internal database format. It means that compliant nodes must follow the same protocol rules and agree on the valid chain and its resulting state. When a node receives a new block, it must check the relevant conditions. Depending on the network, these checks can include:

  • Whether the block follows the required structure.
  • Whether transactions satisfy protocol rules.
  • Whether inputs are available and have not already been spent.
  • Whether signatures and spending conditions are valid.
  • Whether account balances, nonces and execution results are correct.
  • Whether the resulting state matches the required cryptographic commitment.

A node cannot establish the validity of a transaction merely because a wallet, explorer or another participant reports a particular balance. It must verify the relevant information against the ledger rules. This independent verification is a central property of blockchain architecture. It reduces the need to trust a single organisation or database operator to report the correct state. Nevertheless, verification has practical costs. Nodes need computing resources, storage, network access and software that correctly implements the protocol. The design of state management therefore affects not only correctness, but also the resources required to participate in the network.

8.11 State Models and Parallel Processing

The way a blockchain represents state also affects how transactions can be processed. In a UTXO-based system, transactions that spend completely separate outputs can often be validated independently. For example, if one transaction spends UTXO A and another spends UTXO B, and neither transaction depends on the other's outputs or other shared conditions, their validation may be performed in parallel. However, if both transactions attempt to spend the same UTXO, they conflict. Only one can successfully consume that particular output in the accepted ledger. In an account-based system, transactions may read and modify shared account or contract state. For example, two transactions interacting with the same smart contract may depend on the order in which earlier changes are applied. This creates dependencies that can limit straightforward parallel execution. It does not mean that account-based systems cannot use parallel processing. Implementations can analyse transaction dependencies and optimise execution where possible. Similarly, a UTXO model does not guarantee unlimited parallelism. Transactions may still share inputs, depend on common conditions or interact with application-level constraints. The architectural difference is therefore about the structure of dependencies and the opportunities they create for safe parallel processing.

8.12 Architectural Implications: What State Design Determines

State management is one of the most important architectural decisions in a blockchain system. It determines how the network represents ownership, how transactions modify the ledger, what information nodes must maintain and how applications interact with the underlying protocol. The three models illustrate different approaches: Bitcoin uses a relatively direct model based on unspent transaction outputs. Its state is a collection of spendable outputs rather than a database of account balances. Ethereum uses a global account-based execution state. This supports persistent smart contract storage and complex interactions, but transactions can depend on shared mutable state. Cardano extends the UTXO model with datums, redeemers and transaction context. This allows smart contract state to be represented through outputs while retaining explicit input and output dependencies. These choices have consequences for:

  • Transaction design and validation.
  • Storage requirements and historical data access.
  • Smart contract architecture.
  • Parallel processing and transaction conflicts.
  • State verification and cryptographic commitments.
  • The complexity of node and application software.

There is no universal state model that eliminates every trade-off. A blockchain must balance the need for expressive functionality with predictability, security, resource efficiency and the ability of independent participants to verify the ledger. Understanding state is therefore essential to understanding how a blockchain actually works.

Key Takeaways

  1. State represents the current condition of a blockchain ledger, while transaction history records how that condition was produced.
  2. State transitions apply protocol rules to transactions and transform one valid state into another.
  3. Bitcoin represents spendable value through the UTXO set, not through protocol-level account balances.
  4. Ethereum maintains account-based execution state, including balances, nonces, contract code references and persistent storage.
  5. Cardano uses eUTXO, where transaction outputs can carry data that represents smart contract state.
  6. Historical data and current state are related but distinct. A node's ability to access earlier states depends on the data it retains or can retrieve.
  7. Cryptographic commitments help nodes verify state, but they do not replace transaction validation or consensus.
  8. State architecture influences transaction dependencies, storage, execution and opportunities for parallel processing.

Research Note

The terms state, storage, ledger and history are sometimes used interchangeably in general discussions about blockchain technology. In technical analysis, they should be distinguished. A blockchain's current state is not simply a copy of its entire history, and a state commitment is not a substitute for validating the transactions that produced it. These distinctions are essential when comparing different blockchain architectures and evaluating their security, scalability and operational requirements.

09. Consensus And Network Coordination

9.1 Why Does a Blockchain Need Consensus?

A blockchain network consists of independent participants that communicate with one another but do not necessarily trust one another. Each node receives transactions and blocks, checks them against protocol rules and maintains its own view of the ledger. However, a distributed network must solve a fundamental problem: How can independent nodes agree on one accepted sequence of blocks when different participants may receive information at different times, and when some participants may behave dishonestly? This is the purpose of a blockchain consensus mechanism. Consensus allows the network to coordinate around:

  • Which participants are permitted to propose new blocks.
  • Which proposed blocks satisfy the protocol rules.
  • Which chain should be followed when competing versions appear.
  • How the network establishes confidence that accepted transactions will remain in the ledger.
  • How the system responds to delays, failures and malicious behaviour.

Consensus is not simply a vote in which every computer expresses an opinion. It is a collection of protocol rules, cryptographic mechanisms, economic incentives and coordination procedures that allow a distributed network to maintain a consistent ledger.

9.2 Consensus Is More Than Block Production

Block production and consensus are closely connected, but they are not the same process. A participant may successfully produce a candidate block without that block becoming part of the network's accepted chain. Other nodes must still verify it and determine whether it should be adopted. A consensus mechanism therefore performs several related functions:

9.2.1 Participant selection

The protocol determines who may propose or produce a block and under what conditions.

9.2.2 Block validation

Nodes independently check whether the proposed block and its transactions follow the consensus rules.

9.2.3 Chain selection

When multiple competing blocks or chains exist, nodes apply a common rule to determine which valid chain to follow.

9.2.4 Finality or settlement

The protocol provides a way to establish increasing confidence that accepted blocks will not be replaced, or a formal mechanism for finalising them. The precise design differs between blockchain systems. A block producer creates a candidate addition to the ledger. Consensus determines whether that addition becomes part of the network's accepted history.

9.3 The Distributed Coordination Problem

Imagine a network with thousands of independent nodes. One node receives a new block immediately. Another receives it several seconds later because of network latency. A third temporarily loses its connection. During that interval, some nodes may have different views of the latest block. This does not automatically mean that the network has failed. Distributed systems must operate despite delays, temporary disconnections and differences in the order in which information arrives. Consensus protocols establish rules for handling these situations. For example, two miners may produce different valid Bitcoin blocks at approximately the same time. Both blocks can initially be propagated across the network. Some nodes receive the first block, while others receive the second. The network temporarily has competing versions of the chain. A consensus mechanism provides the rules that allow nodes to converge on one accepted history as additional blocks are produced and propagated. This is a central challenge of distributed coordination: participants must be able to reach agreement without requiring every message to arrive simultaneously.

9.4 Bitcoin: Proof of Work and Nakamoto Consensus

Bitcoin uses Proof of Work (PoW) as its Sybil-resistance mechanism and block-production system. Mining participants compete to find a block header whose cryptographic hash satisfies the network's current difficulty target. Finding a valid hash requires computational work. Checking the result is comparatively straightforward for other nodes. This creates an important asymmetry:

  • Producing a valid proof requires substantial computational effort.
  • Verifying a proposed proof requires relatively little work.

A miner that discovers a valid block broadcasts it to the network. Other nodes independently check the block, including its proof of work, transactions and compliance with Bitcoin's consensus rules. A block that fails validation is not accepted simply because a miner has produced it.

Chain selection

Bitcoin nodes follow the valid chain with the greatest accumulated proof of work. This is often described informally as the longest-chain rule. However, the technically important measure is accumulated work, not simply the number of blocks. Two chains can contain the same number of blocks but represent different amounts of total computational work. When competing valid chains appear, nodes select the chain with the most accumulated work according to the protocol. As additional blocks are added, one branch generally gains an advantage and the competing branch becomes stale.

Why confirmations matter

When a transaction is included in a Bitcoin block, it receives its first confirmation. Each subsequent block built on top of that block adds another confirmation. More confirmations generally mean that replacing the transaction would require an increasingly difficult reorganisation of the chain. However, Bitcoin does not provide the same kind of formal checkpoint finality used by Ethereum's Proof-of-Stake consensus. Its transaction confidence increases as more work accumulates on top of the block. This is why users and services often apply confirmation requirements that depend on the value and risk of a transaction. The number of confirmations needed is not a universal guarantee against every possible attack. It is a practical way to evaluate settlement confidence.

9.5 Ethereum: Proof of Stake and Gasper

Ethereum uses Proof of Stake (PoS). Instead of competing through computational hashing power, validators participate by depositing ETH as stake and following the consensus protocol. The stake provides an economic basis for participation and creates incentives to behave according to the rules. Validators can receive rewards for correct participation and face penalties for certain forms of misconduct or failure. Ethereum's consensus mechanism is commonly known as Gasper. It combines two important components:

  • Casper Friendly Finality Gadget (Casper FFG).
  • Latest Message Driven Greediest Heaviest Observed SubTree (LMD-GHOST).

These components perform different but complementary functions.

Block proposals and attestations

Ethereum divides time into slots, which are grouped into epochs. A validator is selected to propose a block for a particular slot. Other validators receive the proposed block, check its validity and participate in consensus by issuing attestations. An attestation is a signed statement expressing a validator's view of the chain and its relevant checkpoints. The combined attestations help the network determine which chain should be preferred.

Fork choice: LMD-GHOST

Sometimes two competing blocks may exist for the same position in the chain. This can happen because of network delays or competing proposals. Ethereum uses LMD-GHOST to determine which branch should be followed. The algorithm considers validator attestations and their effective stake weights when determining the preferred chain. This allows nodes to coordinate their view of the latest part of the blockchain even when information arrives at different times.

Finality: Casper FFG

Ethereum also provides a formal finality mechanism. Validators vote on checkpoints associated with epochs. When the required supermajority conditions are met, checkpoints can become justified and then finalized. Finality is an important distinction between Ethereum and Bitcoin. A finalized block is not expected to be reverted during normal operation. Reverting finalized history would require a serious consensus failure and would involve substantial economic penalties for misbehaving stake. Ethereum's finality mechanism therefore provides a formal settlement property rather than relying only on the accumulation of additional blocks.

9.6 Cardano: Ouroboros Proof of Stake

Cardano uses the Ouroboros family of Proof-of-Stake consensus protocols. Its current consensus design uses Ouroboros Praos. Rather than relying on miners competing to solve computational puzzles, the protocol selects stake pools to produce blocks. The probability of selection is related to the stake controlled by a pool.

Slots and epochs

Cardano divides time into two organisational units:

  • Slots — short periods during which a block may be produced.
  • Epochs — larger periods containing a defined number of slots.

In Ouroboros Praos, slot leaders are selected using cryptographic mechanisms, including a Verifiable Random Function (VRF). The selection process is designed to provide randomness while limiting the ability of an adversary to predict future block producers. A selected slot leader can produce a block and distribute it to the network. Other nodes independently validate the block and apply the chain-selection rules.

Chain selection

Cardano nodes may receive competing valid chains. They use the protocol's chain-selection rules to determine which chain to adopt. In the simplified description, nodes follow the longest valid chain, with additional density and protocol conditions used when comparing competing branches. This means that block height alone is not always sufficient to determine which candidate chain should be selected. The protocol also accounts for the structure and growth of the competing chains.

Settlement and security

Cardano does not use Ethereum's Casper FFG checkpoint-finality mechanism. Instead, Ouroboros provides security through its Proof-of-Stake design, chain-selection rules and settlement properties. Recent blocks may remain subject to rollback, while older blocks become increasingly settled under the protocol's security assumptions. This distinction is important: Proof of Stake is not one universal consensus algorithm. Ethereum and Cardano both use stake-based participation, but their consensus protocols have different designs and finality mechanisms.

9.8 Forks, Competing Chains and Network Recovery

A fork occurs when a blockchain has more than one competing version of its history. Forks can arise for several reasons:

  • Two valid blocks are produced at approximately the same time.
  • Network delays cause participants to receive different blocks first.
  • A temporary network partition separates groups of nodes.
  • Consensus rules change and different software versions interpret them differently.
  • An attacker deliberately attempts to create an alternative chain.

Not all forks have the same meaning or consequences.

Temporary forks

A temporary fork can occur during normal network operation. For example, two Bitcoin miners may produce valid blocks extending the same previous block. Different nodes may initially adopt different branches. As new blocks are added, the chain with the greatest accumulated proof of work becomes preferred. In Proof-of-Stake systems, fork-choice rules and validator messages serve a comparable coordination purpose, although their technical mechanisms differ. Temporary forks are therefore not automatically evidence of a failed blockchain.

Protocol forks

A protocol fork is different. It can occur when changes to consensus rules cause different groups of nodes to disagree about which blocks are valid. A hard fork introduces rules that are not backward-compatible with the previous protocol. Nodes that do not upgrade may reject blocks accepted by upgraded nodes, creating the possibility of permanently separate networks. A soft fork introduces more restrictive rules that can remain compatible with the previous rules from the perspective of non-upgraded nodes. Protocol upgrades therefore require careful coordination, testing and adoption by the network's participants.

Network partitions

A network partition occurs when groups of nodes cannot communicate normally. Each group may temporarily maintain a different view of the chain. The consensus protocol must be able to handle the resulting divergence and establish a consistent chain when communication resumes. The ability to recover depends on the protocol's assumptions about network connectivity, timing, participant behaviour and economic security.

9.9 Security Assumptions and Economic Incentives

Consensus mechanisms must protect a network against participants who may attempt to manipulate block production or chain selection. Different protocols use different resources to make attacks difficult or expensive.

Proof of Work

Bitcoin's security depends in part on the computational cost of producing valid proof of work. An attacker attempting to replace accepted history must construct an alternative chain with sufficient accumulated work to overcome the chain followed by honest nodes. This can require enormous computational resources and electricity.

Proof of Stake

Ethereum and Cardano use stake-based mechanisms. The protocol connects participation to economic resources and applies rules designed to discourage dishonest behaviour. Depending on the protocol, participants may lose rewards, face penalties or have stake subjected to slashing for specific violations.

The importance of assumptions

No consensus mechanism provides security independently of its assumptions. These can include:

  • The distribution of mining power or stake.
  • The proportion of participants following protocol rules.
  • Network communication and timing conditions.
  • The quality of node software and cryptographic implementations.
  • The economic incentives influencing participants.
  • The ability of the network to respond to attacks and failures.

A security claim must therefore be understood in the context of the particular protocol. For example, a statement that a network is secure because it uses Proof of Stake is incomplete without examining its validator selection, voting, fork-choice and penalty mechanisms. Consensus security is a property of the complete system, not simply the name of its consensus algorithm.

9.10 Consensus, Decentralisation and Governance

Consensus and governance are related, but they are not identical. Consensus determines how nodes agree on valid blocks and the accepted chain under the existing protocol rules. Governance concerns how decisions about the protocol itself are proposed, discussed, approved and implemented. A blockchain may use a decentralised consensus mechanism while still having concentrated influence over important development or infrastructure decisions. For example:

  • A small number of mining pools may control a large share of mining activity.
  • A limited number of entities may operate a significant proportion of validators.
  • Software development may depend heavily on a relatively small group of contributors.
  • Infrastructure providers may influence how participants access the network.

These factors do not automatically invalidate the consensus mechanism, but they matter when evaluating the practical distribution of power. It is useful to distinguish: Consensus decentralisation — how independent participants validate blocks and coordinate around the accepted chain. Economic decentralisation — how mining power, stake, capital and rewards are distributed. Governance decentralisation — how decisions about protocol development and changes are made. Infrastructure decentralisation — how widely distributed the systems and services supporting the network are. A blockchain's decentralisation cannot be evaluated accurately by looking at only one of these dimensions.

9.11 Coordination Without a Central Controller

Consensus allows a blockchain to coordinate participants without requiring a central operator to approve every transaction or select every block. Each node follows protocol rules and independently evaluates the information it receives. Block producers contribute candidate blocks. Other nodes validate them. Chain-selection rules determine which history should be followed. This creates a system in which agreement emerges from the interaction of independent participants following common rules. However, decentralised coordination does not mean that every participant has equal influence, equal resources or identical responsibilities. A miner, validator, full node, wallet and application may all interact with the same blockchain while performing different functions. The consensus mechanism coordinates the production and acceptance of the ledger, but it does not make every participant's role identical. This distinction is important when evaluating claims about decentralisation, security and network independence.

9.12 Architectural Trade-offs and the Meaning of Finality

Consensus design affects the performance, security and operational characteristics of a blockchain. A protocol must balance several objectives:

  • Security against malicious participants.
  • Reliable agreement despite network delays.
  • Resistance to double spending and history manipulation.
  • Reasonable transaction settlement times.
  • Resource efficiency.
  • Open participation and decentralised control.
  • Predictable recovery from temporary failures.

Bitcoin's Proof-of-Work design uses accumulated computational effort to protect its chain history. Its settlement confidence increases as additional blocks are built on top of a transaction. Ethereum combines stake-based validator participation, fork choice and checkpoint finality. It provides a formal finality mechanism, but this depends on the assumptions and conditions of its consensus protocol. Cardano uses Ouroboros Praos, with stake-weighted slot-leader selection and chain-selection rules designed to maintain a secure and consistent chain. These approaches cannot be compared accurately by looking only at block time or transaction confirmation speed. A faster block interval does not automatically mean stronger security. A formal finality mechanism is not identical to probabilistic settlement. A higher number of validators does not necessarily mean that economic influence or infrastructure is evenly distributed. The relevant question is not simply how quickly a block appears, but how the protocol establishes that the block belongs to the accepted chain and how difficult it would be to reverse that decision.

Key Takeaways

  1. Consensus enables independent blockchain participants to coordinate around one accepted ledger.
  2. Block production and consensus are different processes. A proposed block must still be validated and accepted under the protocol rules.
  3. Bitcoin uses Proof of Work and selects the valid chain with the greatest accumulated work.
  4. Ethereum uses Gasper, combining LMD-GHOST fork choice with Casper FFG checkpoint finality.
  5. Cardano uses Ouroboros Praos, which selects stake pool block producers through a slot-based Proof-of-Stake protocol.
  6. Forks can be temporary consequences of network timing or permanent divisions caused by incompatible protocol rules.
  7. Finality has different meanings across blockchain systems and should not be reduced to a universal number of confirmations.
  8. Decentralisation includes consensus, economic, governance and infrastructure dimensions.
  9. Security depends on assumptions and incentives, not merely on the name of a consensus mechanism.

Research Note

The word consensus is often used as if it described a single event in which all network participants agree simultaneously. In practice, distributed consensus is a continuing coordination process. Nodes receive information at different times, validate proposed blocks independently, apply chain-selection rules and establish confidence or finality according to the protocol. Proof of Work and Proof of Stake are not complete descriptions of every part of a consensus mechanism. They describe important ways of resisting Sybil attacks and organising block production, but chain selection, validation, incentives and settlement are equally important parts of the architecture.

10. Protocol Rules And Network Upgrades

10.1 What Are Blockchain Protocol Rules?

A blockchain protocol is a set of technical rules that define how the network operates. These rules determine what nodes must accept, reject, verify and communicate. They cover areas such as:

  • The structure of blocks and transactions.
  • Cryptographic signatures and validation requirements.
  • Transaction fees and resource limits.
  • Block production and consensus.
  • Network communication.
  • Smart contract execution.
  • State transitions and protocol parameters.
  • The conditions under which new blocks become valid.

A blockchain node uses these rules to decide whether incoming information is acceptable. For example, a node may receive a transaction that appears correctly formatted but violates a spending condition. The node must reject it even if another participant claims that the transaction is valid. The same principle applies to blocks. A block producer cannot create new rules simply by including them in a block. Other nodes must be able to verify the block under the protocol they follow. Protocol rules therefore define the common technical framework that allows independent participants to operate as part of one network.

10.2 Why Do Blockchain Protocols Need Updates?

No software system remains permanently complete. Blockchain protocols evolve as developers and researchers discover weaknesses, improve existing mechanisms and propose new capabilities. An update may be necessary for several reasons:

Security improvements

A vulnerability in software, cryptographic implementation or protocol logic may require a correction.

Performance and efficiency

Developers may improve how nodes process transactions, store information or communicate with other participants.

New functionality

A network may introduce new transaction capabilities, smart contract features, cryptographic tools or governance mechanisms.

Scalability

Changes may aim to improve transaction processing, reduce resource requirements or support more complex applications.

Protocol maintenance

Software dependencies, implementation problems and changing technical requirements may require updates even when users do not notice a new feature. Not every software update changes the blockchain's consensus rules. Some updates improve wallet interfaces, node performance, networking or application programming interfaces without changing which blocks are considered valid. This distinction is important because consensus-rule changes require much more careful coordination than ordinary software maintenance.

10.3 Software Updates and Consensus Changes Are Different

A blockchain node is software that implements the protocol and communicates with the network. However, a software release does not automatically change the protocol. Consider three broad categories of changes:

Type of changeWhat it affectsNetwork-wide consensus change required?
User interface or wallet improvementHow people interact with the networkUsually no
Networking or performance improvementHow nodes communicate or operateNot necessarily
Consensus-rule changeWhich blocks or transactions are validYes, coordination is required

A wallet may receive an update that improves transaction display without changing the blockchain itself. A node implementation may improve memory usage while continuing to validate exactly the same blocks as before. By contrast, changing the conditions under which a block is valid can affect whether different nodes agree on the same chain. This is why protocol upgrades must be classified according to their technical impact rather than simply their software version number.

10.4 Soft Forks: Introducing More Restrictive Rules

A soft fork is a protocol change that introduces more restrictive validity rules while preserving compatibility with the previous rules in a specific sense. Under a soft fork:

  • Some blocks or transactions that were previously valid become invalid under the new rules.
  • Structures that were already invalid remain invalid.
  • Older software may still recognise blocks produced under the new rules as valid according to its older, less restrictive interpretation.
  • Updated nodes enforce the additional restrictions.

This compatibility is important, but it does not mean that old software fully understands or enforces the new features. Older nodes may not recognise the new functionality or may be unable to verify all of its additional conditions. For example, a soft fork can introduce a new transaction rule that updated nodes enforce while keeping the resulting blocks acceptable to older nodes under their existing validation rules. Bitcoin has used soft-fork upgrades to introduce important protocol improvements. Segregated Witness (SegWit) is a well-known example. It changed transaction structure and introduced new validation capabilities through a backward-compatible deployment design. The exact deployment mechanism depends on the particular proposal and activation method. A soft fork is therefore not simply a small update. It can introduce significant changes while preserving a degree of compatibility with older software.

10.5 Hard Forks: Changing Compatibility with Previous Rules

A hard fork is a protocol change that makes some structures valid under the new rules even though they were invalid under the previous rules. Older software may reject blocks that upgraded software accepts. This creates a compatibility problem. If some participants continue operating under the old rules while others follow the new rules, the network may split into separate chains. A hard fork therefore requires careful coordination and adoption of compatible software by the participants whose nodes must validate the new rules. The consequences depend on how the upgrade is implemented and adopted. A hard fork does not automatically mean that a permanent split will occur. If participants coordinate around the upgrade and adopt the new protocol, the network can continue as one chain under the new rules. However, if substantial groups maintain incompatible rule sets, separate networks may continue to operate. The distinction between soft forks and hard forks is particularly important because a protocol upgrade can affect the validity of the entire blockchain history from the point of activation.

10.6 Bitcoin: BIPs and Voluntary Network Adoption

Bitcoin uses the Bitcoin Improvement Proposal (BIP) process to document and discuss proposed changes. A BIP provides a structured way to describe a technical improvement, its motivation, its design and its implications. A proposal may concern:

  • Consensus rules.
  • Networking.
  • Wallet or application standards.
  • Node interfaces.
  • Other technical aspects of the Bitcoin ecosystem.

Anyone can contribute ideas and participate in technical discussions, although producing a complete and well-reviewed protocol proposal requires considerable expertise.

From proposal to implementation

A simplified Bitcoin improvement process may include:

  1. An idea or problem is identified.
  2. A proposal is discussed with developers and other participants.
  3. A BIP documents the proposed design.
  4. The proposal is reviewed and revised.
  5. Developers implement the change in software.
  6. The implementation is tested.
  7. If the proposal changes consensus rules, an appropriate activation mechanism is considered.
  8. Participants decide whether to adopt the new software and follow the updated rules.

Publication of a BIP does not mean that the proposal has been approved or will become part of Bitcoin. A BIP is a technical proposal and coordination document, not an instruction that automatically changes the network. Who decides? Bitcoin does not have a central organisation with the authority to impose every protocol change on all participants. Developers can propose and implement changes, but users and node operators choose which software to run. Miners also play an important role in some upgrade activation mechanisms. The influence of these groups differs depending on the type of proposal. A change to consensus rules must achieve sufficient coordination for the network to continue operating under compatible rules. This is one reason why Bitcoin protocol changes can take considerable time. The cautious process reflects the importance of maintaining predictable rules for a network that secures valuable economic activity.

10.7 Ethereum: EIPs and Coordinated Client Upgrades

Ethereum uses Ethereum Improvement Proposals (EIPs) to describe and coordinate potential changes. An EIP can propose a technical improvement, a new standard or a change to the protocol. Examples include:

  • Core protocol changes.
  • Changes to transaction processing.
  • Improvements to the Ethereum Virtual Machine.
  • Networking specifications.
  • Application standards such as ERC-20 and ERC-721.

Not every EIP changes the consensus rules. For example, an application standard may be adopted by individual applications without requiring every Ethereum node to implement it. A core protocol change, however, may require a coordinated network upgrade.

How Ethereum upgrades are coordinated

A simplified process looks like this:

  1. A proposal is submitted and documented as an EIP.
  2. Developers and community participants discuss the technical design.
  3. Alternative approaches and potential risks are evaluated.
  4. The proposal may be tested and implemented in client software.
  5. Core developers and other stakeholders discuss whether it should be included in a network upgrade.
  6. The required changes are incorporated into the relevant Ethereum clients.
  7. The upgrade is scheduled for a specific activation point.
  8. Node operators and validators upgrade their software to remain compatible with the network.

Ethereum uses multiple independently developed clients. This is an important architectural feature: the protocol is not implemented by only one software application. Clients must implement the same required protocol changes so that they continue to agree on which blocks are valid. Is Ethereum governed by a central vote? Ethereum does not use one universal on-chain voting procedure in which token holders directly approve every protocol upgrade. Its governance process involves technical discussions, research, client developers, application developers, node operators, validators and other community participants. EIPs provide a common framework for documenting and discussing proposed changes. A proposal's publication does not guarantee adoption. Its inclusion in a network upgrade depends on broader technical and community coordination. This is an important distinction between Ethereum's governance process and systems that use formal on-chain governance actions.

10.8 Cardano: Protocol Upgrades and On-Chain Governance

Cardano has developed a structured approach to protocol evolution. Its architecture uses the Hard Fork Combinator, a mechanism designed to support transitions between protocol eras while preserving the continuity of the chain. This is an important difference from the traditional interpretation of a hard fork as an event that necessarily creates two separate networks. In Cardano, a hard fork can represent an agreed transition to a new set of protocol rules at a specified point. The Hard Fork Combinator allows the network to move between protocol eras without requiring the blockchain's historical record to be discarded or the chain to restart.

Cardano Improvement Proposals

Cardano uses Cardano Improvement Proposals (CIPs) to document proposed changes and standards. CIPs can describe new functionality, technical improvements, application interfaces and governance-related mechanisms. However, a CIP is not automatically a protocol upgrade. The implementation and approval requirements depend on the type of change.

On-chain governance

Cardano's Conway era introduced on-chain governance based on CIP-1694. Its governance structure includes three main bodies:

  • Delegated Representatives (DReps) — represent the voting interests of ADA holders who delegate their voting power.
  • Stake Pool Operators (SPOs) — operate stake pools and participate in specified governance decisions.
  • Constitutional Committee (CC) — evaluates whether governance actions comply with the Cardano Constitution.

Different types of governance actions require different combinations of approvals. Hard-fork initiation is one such action. Under the current governance framework, the proposed upgrade is submitted on-chain and must satisfy the applicable approval requirements. The relevant participants must also prepare their infrastructure and install compatible node software. An on-chain vote alone does not install new software or guarantee that every node is technically ready.

The importance of the Hard Fork Combinator

The Hard Fork Combinator manages the transition between protocol eras. It allows Cardano to preserve the continuity of the chain while introducing new rules and capabilities. This design has supported major transitions in the network's history, including Shelley, Alonzo and Conway. The Cardano example demonstrates that the term hard fork does not always imply a permanent division of the network. Its practical meaning depends on the protocol's upgrade architecture and how participants coordinate the transition.

Bitcoin, Ethereum and Cardano all rely on proposals, technical review, implementation and network coordination. However, their approaches to governance and upgrade activation differ.

10.10 Testing, Activation and Network Readiness

A protocol upgrade should not move directly from an idea to the production network without extensive testing. A simplified upgrade lifecycle includes several stages.

Research and specification

Developers identify a problem or improvement and document the intended behaviour.

Technical review

The proposed change is examined for correctness, compatibility, security and potential unintended consequences.

Implementation

Developers modify node software and other relevant components.

Testing

The implementation is tested through automated tests, simulations, test networks and other validation methods.

Coordination

Participants determine whether the proposal is ready, how it will be activated and what software versions are required.

Activation

The network reaches the specified activation point, such as a block height, timestamp, epoch or another protocol-defined condition.

Post-upgrade monitoring

Developers and operators monitor network behaviour, software errors and unexpected consequences. The exact stages vary between blockchain systems. A successful software test does not prove that an upgrade is risk-free. Testing reduces uncertainty, but complex distributed systems can still reveal unexpected behaviour after deployment. This is why protocol upgrades require careful preparation and monitoring.

10.11 What Can Go Wrong During an Upgrade?

Protocol upgrades introduce technical and coordination risks. Several problems deserve particular attention.

Software bugs

A new implementation may contain an error that causes nodes to calculate different results. If the error affects consensus validation, different nodes may disagree about block validity.

Incomplete adoption

Some node operators may fail to install the required update before activation. Depending on the type of change, they may lose compatibility with the upgraded network.

Incompatible implementations

If different clients implement the same specification incorrectly or interpret it differently, they may disagree about valid transactions or blocks. This is especially important in networks with multiple independent client implementations.

Governance disagreement

Participants may disagree about the proposed changes, their timing or their consequences. If incompatible groups continue using different protocol rules, the network may divide.

Economic and operational consequences

An upgrade may change transaction costs, resource requirements, validator responsibilities or application behaviour. A technically valid upgrade can still create difficulties for wallets, exchanges, infrastructure providers and smart contract developers. These risks demonstrate why protocol changes are not merely programming tasks. They are coordinated changes to a distributed economic and technological system.

10.12 Protocol Evolution and the Stability of a Blockchain

A blockchain must balance two objectives that can sometimes conflict. On one hand, it needs to evolve. Security weaknesses must be addressed, software must improve and new capabilities may be necessary for the network to remain useful. On the other hand, participants depend on stable and predictable rules. Applications, wallets, exchanges, businesses and users build systems around the existing protocol. Unexpected changes can create operational risks and undermine confidence in the network. This creates a central architectural trade-off: A blockchain must be capable of changing its rules without losing the coordination that makes it a blockchain. Bitcoin, Ethereum and Cardano approach this challenge differently. Bitcoin emphasises cautious protocol changes and broad voluntary adoption. Ethereum coordinates upgrades through EIPs, technical discussion and implementation across multiple clients. Cardano combines protocol-era transitions with a formal on-chain governance framework. None of these approaches eliminates disagreement, technical risk or the need for careful review. A successful upgrade depends on more than the quality of the code. It also requires clear specifications, reliable implementations, transparent communication and sufficient coordination among the participants who maintain the network.

Key Takeaways

  1. Protocol rules define how nodes validate transactions, blocks and state transitions.
  2. Not every software update changes consensus rules. Interface, performance and networking improvements may not require a network-wide consensus change.
  3. A soft fork introduces more restrictive rules while preserving a degree of compatibility with older software.
  4. A hard fork makes some previously invalid structures valid, potentially creating incompatibility with older software.
  5. Bitcoin uses BIPs to document proposed improvements and relies on voluntary adoption and coordination.
  6. Ethereum uses EIPs and coordinates core protocol upgrades across its independent clients and network participants.
  7. Cardano uses CIPs, on-chain governance actions for specified decisions and the Hard Fork Combinator to support protocol-era transitions.
  8. Testing and activation are essential parts of a safe upgrade process.
  9. Governance and technical implementation are different. Approving a proposal does not automatically install or correctly implement it.
  10. Protocol evolution requires a balance between innovation, security, compatibility and network stability.

Research Note

A protocol proposal, a software release, a governance decision and an activated network upgrade are four different things. A proposal describes a possible change. Software implements it. Governance and network coordination determine whether and how it is adopted. Activation makes the new rules effective under the specified protocol conditions. Confusing these stages can lead to inaccurate conclusions about who controls a blockchain or how quickly its rules can change. The most useful question when evaluating an upgrade is not simply who proposed it, but which rules are changing, who must implement them, how activation is coordinated and what happens to participants who do not upgrade.

11. Modular And Layered Blockchain Architecture

11.1 Why Do Blockchain Systems Use Layers?

A blockchain is a complex technological system. It must communicate across a distributed network, order transactions, execute them, update its state and make the information available for independent verification. In an earlier generation of blockchain designs, these responsibilities were generally performed together by one blockchain network. As demand for blockchain applications increased, developers began exploring ways to separate some of these responsibilities. This approach is known as modular blockchain architecture. Instead of requiring one network to perform every task, a modular architecture allows specialised components or networks to provide different functions. For example:

  • One layer can execute transactions and update application state.
  • Another can establish transaction ordering.
  • Another can provide data availability.
  • A settlement layer can verify execution results and resolve disputes.

The objective is to allow different parts of the system to specialise while working together. However, modularity is not simply a matter of creating more layers. The connections between them must preserve the security, correctness and availability of the overall system.

11.2 Monolithic Architecture: Multiple Functions in One Network

A monolithic blockchain performs its principal blockchain functions within one integrated network. In this design, the same underlying protocol is responsible for coordinating transaction ordering, making block data available and validating the resulting state transitions. Bitcoin is a useful example of an integrated blockchain architecture. Its nodes receive transactions, verify them according to Bitcoin's rules and maintain the accepted chain. Miners produce blocks through Proof of Work, while full nodes independently validate those blocks. Ethereum Layer 1 also provides an integrated blockchain environment, although its software architecture separates execution and consensus responsibilities between different client components. This distinction matters: a monolithic blockchain does not necessarily mean that one software program performs every task. It means that the principal blockchain functions are provided together by the same underlying network rather than distributed across separate specialised chains.

Potential advantages

An integrated architecture can offer:

  • A relatively direct relationship between transactions and the network that validates them.
  • A common set of protocol rules.
  • Fewer external dependencies between separate blockchain networks.
  • A unified environment for applications and settlement.

Potential limitations

As usage grows, one network may face competing demands. It must process transactions, communicate information, maintain state, provide data and support independent verification. Increasing capacity in one area can create additional pressure elsewhere. For example, larger blocks may increase storage, bandwidth and processing requirements for nodes. A design that increases transaction throughput but makes independent verification significantly more expensive may create new centralisation pressures. This is one reason why developers investigate specialised layers.

11.3 Modular Architecture: Separating Responsibilities

A modular blockchain architecture divides the system's functions among specialised components or networks. Instead of requiring one chain to perform every task, different parts of the system can provide complementary services. A common conceptual model identifies four principal functions:

  1. Execution — processes transactions and calculates state changes.
  2. Consensus — establishes agreement about transaction ordering and the accepted chain.
  3. Data Availability — provides assurance that the transaction data required for verification has been published and can be accessed.
  4. Settlement — verifies execution results, handles disputes and may provide a common environment for final settlement.

These functions are related, but they are not interchangeable. A modular architecture may distribute them across two, three or more layers, depending on the system's design. Not every architecture requires a separate settlement layer. Some networks combine settlement with consensus or provide other arrangements. The important principle is functional separation, not a fixed number of layers.

11.4 Execution Layer: Where Transactions Change State

The execution layer is responsible for processing transactions according to the rules of a particular blockchain environment. It determines whether transactions are valid and calculates their effects on the system's state. This may include:

  • Updating account balances.
  • Consuming and creating UTXOs.
  • Executing smart contracts.
  • Checking transaction conditions.
  • Calculating transaction fees and resource consumption.
  • Producing the resulting state or state commitment.

In an integrated blockchain, execution may take place directly within the main network. In a modular architecture, execution can be moved to a specialised environment. For example, Ethereum Layer 2 rollups process transactions outside Ethereum Layer 1 and submit information about their activity to the underlying network. This allows a rollup to handle many transactions without requiring every transaction to be executed individually by every Ethereum Layer 1 node. However, the execution layer still needs a way to establish that its results are correct and that the information required to verify them is available. This is where settlement and data availability become important.

11.5 Consensus Layer: Establishing Transaction Order

The consensus function allows participants to agree on the order of transactions or data submitted to the blockchain system. Transaction order matters because the same transactions can produce different results when processed in a different sequence. For example, two transactions interacting with the same account or smart contract may depend on the state created by the preceding transaction. A modular architecture can separate the responsibility for ordering data from the execution of that data. A specialised consensus network may establish an agreed sequence of transaction data without executing every application transaction itself. This creates an important distinction: Consensus over ordering does not automatically mean that every transaction has been executed and verified. A system must still provide a mechanism for checking the resulting state transitions. A consensus layer may also provide other services, including block production, network security and the ordering of data submitted by multiple applications. Its exact responsibilities depend on the architecture.

11.6 Data Availability Layer: Can the Data Be Retrieved and Verified?

Data availability is one of the most important concepts in modular blockchain design. When a blockchain publishes a block, other participants need access to the information required to verify it. A block header or a cryptographic commitment may summarise a large amount of data, but a summary alone is not necessarily sufficient for independent verification. Participants may need the underlying transaction data to:

  • Reconstruct the state.
  • Verify transaction execution.
  • Detect invalid state transitions.
  • Reproduce the history of an application.
  • Continue operating if a central operator becomes unavailable.

This creates the data availability problem. A network must provide confidence that the complete data required for verification has actually been published and is accessible to participants.

Data availability is not the same as permanent storage

An important distinction must be made between data availability and data retrievability. Data availability concerns whether the required data was published and can be accessed for verification within the relevant protocol conditions. Data retrievability concerns whether historical information can still be obtained later. A blockchain may guarantee data availability for a defined period without guaranteeing that every piece of historical data will remain accessible forever. This distinction is particularly important for systems using temporary data storage mechanisms.

Data Availability Sampling

Some modular architectures use Data Availability Sampling (DAS). Instead of requiring every light node to download an entire block, nodes can request small, randomly selected portions of the data. With appropriate erasure coding and cryptographic commitments, successful sampling provides confidence that the complete data has been published. This approach can reduce the amount of information that individual light nodes must download. However, data availability sampling is not the same as executing every transaction or proving that the resulting state is valid. It addresses a specific problem: whether the data needed for verification has been made available.

11.7 Settlement Layer: Verifying Results and Resolving Disputes

The settlement layer provides a mechanism for establishing the status of execution results and resolving disagreements. Depending on the architecture, it may:

  • Verify validity proofs.
  • Process fraud proofs or challenges.
  • Establish settlement conditions.
  • Record commitments to another chain's state.
  • Provide a common environment for interactions between execution systems.

Settlement is particularly important when a separate execution layer depends on another blockchain for security. For example, an optimistic rollup can publish transaction data and state commitments to Ethereum. Its proposed state changes are treated according to an optimistic model, with a challenge mechanism that allows invalid results to be disputed. A zero-knowledge rollup follows a different approach: it submits cryptographic validity proofs that allow the settlement layer to verify the correctness of specified state transitions. The exact proof systems and verification mechanisms vary between rollups. Not every modular blockchain has a separate settlement layer. Some designs combine settlement with another component, while others use different arrangements for verifying execution results. The term should therefore be understood as a function rather than as a mandatory physical layer in every blockchain architecture.

11.8 How the Layers Work Together

Consider a simplified modular system that processes transactions through several specialised components. A user submits a transaction to an execution environment. The system processes the transaction and calculates a proposed state change. The transaction data is published to a data availability layer, while a consensus mechanism establishes the ordering of that data. The execution system produces a commitment or proof representing its result. A settlement layer may then verify the proof or provide a mechanism for challenging an incorrect result. A simplified sequence looks like this:

  1. A user submits a transaction.
  2. The execution layer processes it.
  3. The transaction data is made available.
  4. The consensus mechanism establishes the relevant ordering.
  5. The execution system produces a state commitment or proof.
  6. The settlement mechanism verifies or finalises the result according to its rules.
  7. Applications and users interact with the updated state.

The sequence is conceptual. Actual systems may perform several of these operations simultaneously or in a different order. The essential requirement is that the components provide compatible guarantees. If execution is separated from data availability, for example, the system must still ensure that the information needed to reconstruct and verify execution results can be obtained. If settlement depends on proofs, those proofs must be correctly generated and verified. A modular architecture works only when its components are securely connected.

11.9 Ethereum and Layer 2 Rollups: A Practical Example

Ethereum provides an important example of how an integrated Layer 1 can support specialised execution environments. Layer 2 rollups process transactions outside the main Ethereum execution environment and publish information about their activity to Ethereum. This reduces the amount of execution work that must be performed directly on Layer 1. Two major rollup categories are:

Optimistic rollups

Optimistic rollups generally assume that submitted state transitions are valid unless someone successfully challenges them. They use fraud-proof mechanisms to dispute incorrect state changes. Transaction data is published to Ethereum so that independent participants can reconstruct and verify the rollup's activity.

Zero-knowledge rollups

Zero-knowledge rollups use cryptographic validity proofs to demonstrate that a batch of state transitions follows the relevant execution rules. Ethereum verifies the proof according to the rollup's verification mechanism. However, validity proofs and data availability solve different problems. A validity proof can establish that a particular state transition is correct, but users still need access to the relevant state data to reconstruct balances, interact with applications and continue using the system. Both rollup categories therefore depend on carefully designed arrangements for execution, verification and data availability. What does Ethereum provide? Depending on the rollup design, Ethereum can provide:

  • A settlement environment.
  • Consensus over published data.
  • Data availability through transaction calldata or blobs.
  • Verification of proofs or dispute mechanisms.

The exact security guarantees depend on how each rollup is implemented. A Layer 2 network should not be assumed to inherit every security property of Ethereum automatically. Its proof system, data availability arrangements, upgrade controls, bridge design and operational dependencies all matter.

11.10 Celestia: A Data Availability-Focused Modular Network

Celestia is an example of a blockchain network designed around modular architecture. Rather than requiring every application to execute its transactions on Celestia itself, the network focuses on providing consensus and data availability services for other systems. Applications and execution environments can publish transaction data to Celestia and use its mechanisms to establish that the data has been made available. One of its important technologies is Data Availability Sampling. Celestia uses erasure coding and cryptographic data commitments to allow light nodes to sample portions of block data. This makes it possible to verify data availability without downloading every part of every block. Celestia also uses Namespaced Merkle Trees, which organise data so that applications can retrieve information associated with their own namespace. This architecture allows different execution environments to use a shared data availability network. However, Celestia's data availability service does not mean that Celestia automatically executes every application transaction or verifies every application-specific state transition. Those responsibilities belong to the relevant execution and settlement systems. This illustrates the central idea of modular architecture: specialised networks can provide different services while remaining part of a larger technological stack.

11.11 Networking: The Communication Fabric Across Layers

Networking connects the different components of a blockchain system. It enables nodes to discover peers, exchange transactions, propagate blocks, request information and communicate with other services. In a modular architecture, communication becomes especially important because different layers may operate as separate networks. They need mechanisms for exchanging:

  • Transaction data.
  • Block commitments.
  • Execution results.
  • Validity or fraud proofs.
  • Consensus messages.
  • Settlement information.
  • Cross-layer messages and instructions.

Networking is not necessarily a separate layer in the same sense as execution or settlement. It is better understood as a communication function that supports the entire architecture. Ethereum illustrates this distinction even within its own Layer 1 software. Its execution clients and consensus clients have distinct networking responsibilities and must also communicate with each other. In a modular system involving several independent networks, communication may require additional protocols, bridges, message relays or specialised interoperability mechanisms. The reliability and security of these connections can become important parts of the overall system's risk profile.

The two approaches can be compared by looking at how they organise the principal blockchain functions.

11.13 Benefits and Risks of Modular Architecture

Modular architecture creates new possibilities, but it also introduces trade-offs.

Potential benefits

Specialisation

Different networks can focus on the functions they are designed to perform.

Scalability

Multiple execution environments may process transactions without requiring every transaction to be executed directly on one base layer.

Flexibility

Developers can select different execution environments, consensus arrangements and data availability services.

Shared infrastructure

Several applications or rollups may use the same underlying data availability or settlement infrastructure.

Independent development

Specialised components can evolve at different speeds, provided they maintain compatible interfaces and security assumptions.

Potential risks

Additional trust assumptions

A system may depend on external validators, data availability committees, bridges or operators.

Cross-layer complexity

Messages and assets must move between components according to clearly defined rules.

Data availability failures

If transaction data becomes unavailable, users may be unable to reconstruct the state or independently verify operations.

Upgrade coordination

Different components may require separate software upgrades and activation procedures.

Concentration of infrastructure

A system may appear decentralised at the application level while depending heavily on a small number of service providers.

Security interactions

A vulnerability in one component can affect the guarantees provided by the entire system. Modularity therefore moves some complexity rather than simply eliminating it. The design challenge is to ensure that specialised components work together without introducing weaknesses that undermine the system as a whole.

11.14 What Modularity Means for the Future of Blockchain Architecture

Blockchain architecture is evolving from systems in which one network performs most functions toward increasingly specialised combinations of networks, protocols and execution environments. This does not mean that monolithic blockchains will disappear. Different applications have different requirements. Some may prioritise direct verification and a unified settlement environment. Others may need specialised execution, high transaction capacity or flexible data availability arrangements. Future blockchain systems may combine:

  • Multiple execution environments.
  • Shared data availability networks.
  • Specialised settlement mechanisms.
  • Different consensus protocols.
  • Cross-chain communication.
  • Application-specific infrastructure.

The result may be a network of interconnected blockchain systems rather than one universal chain performing every task. However, the number of layers is not a measure of technological quality. A modular system must still answer several fundamental questions:

  • Who orders the transactions?
  • Who verifies execution?
  • Where is the transaction data published?
  • How can users recover their state?
  • What happens if a component becomes unavailable?
  • Which security assumptions depend on external participants?
  • How are messages and assets transferred between layers?

The answers determine whether a modular architecture provides meaningful improvements or merely adds complexity. The long-term value of modularity depends on the ability to combine specialised components while preserving independent verification, security and reliable coordination.

Key Takeaways

  1. Monolithic architecture combines the principal blockchain functions within one integrated network.
  2. Modular architecture separates functions among specialised components or networks.
  3. Execution processes transactions and calculates state changes.
  4. Consensus establishes agreement about transaction ordering and the accepted chain.
  5. Data Availability provides assurance that the information needed for verification has been published.
  6. Settlement can verify execution results and resolve disputes, but it is not a separate mandatory layer in every design.
  7. Networking connects the components and enables communication across the architecture.
  8. Ethereum rollups demonstrate how specialised execution environments can use Ethereum for important settlement and data availability services.
  9. Celestia demonstrates a modular network focused on consensus and data availability for other execution environments.
  10. Modularity creates trade-offs. Specialisation and scalability opportunities must be balanced against additional dependencies and security assumptions.

Research Note

The terms Layer 1, Layer 2, execution layer, consensus layer, data availability layer and settlement layer are related, but they do not describe exactly the same things. Layer 1 and Layer 2 usually describe a relationship between blockchain systems. Execution, consensus, data availability and settlement describe functions that those systems perform. A single blockchain can provide several functions, and a modular stack can distribute them across multiple networks. When evaluating a modular blockchain, it is therefore more useful to identify the responsibilities and security guarantees of each component than to rely only on its layer number or marketing terminology.

12. Security, Trade-Offs And Architectural Limits

12.1 Blockchain Architecture Is a System of Interdependent Choices

A blockchain is not secured by one algorithm, one type of cryptography or one software component. Its reliability depends on the interaction of multiple architectural elements:

  • Network communication.
  • Transaction validation.
  • Data structures and storage.
  • Execution environments.
  • Consensus mechanisms.
  • State management.
  • Protocol upgrades.
  • Economic incentives.
  • External infrastructure and services.

Each component contributes to the operation of the network, but each also introduces requirements and possible limitations. For example, a blockchain may use strong cryptographic mechanisms to protect transaction integrity. However, if only a small number of operators can produce or verify blocks, the network may still face centralisation risks. A network may process transactions very quickly, but if independent participants cannot afford the hardware required to verify them, its practical decentralisation may be reduced. Similarly, a blockchain may have a sophisticated consensus protocol, but vulnerabilities in wallets, bridges, smart contracts or external services can still expose users to significant risks. The security of a blockchain must therefore be evaluated as a property of the complete system.

12.2 The Blockchain Trilemma: Security, Scalability and Decentralisation

One of the best-known ideas in blockchain architecture is the blockchain trilemma. It describes the difficulty of maximising three desirable properties at the same time:

  1. Security — resistance to attacks, manipulation and invalid state changes.
  2. Scalability — the ability to process increasing transaction volumes efficiently.
  3. Decentralisation — the distribution of control and verification among independent participants.

These properties are interconnected.

Security

A blockchain must make it difficult for an attacker to manipulate transaction history, create invalid transactions or influence the accepted chain. Security depends on consensus assumptions, cryptographic mechanisms, independent verification, economic incentives and the reliability of implementations.

Scalability

A blockchain must process transactions as demand grows. This involves more than increasing the number of transactions per second. Scalability also concerns:

  • Transaction confirmation and settlement times.
  • Network bandwidth.
  • Computing requirements.
  • Storage requirements.
  • Transaction costs.
  • The ability of independent participants to keep up with the network.

Decentralisation

A decentralised network distributes important responsibilities among independent participants. These responsibilities can include block production, validation, software development, infrastructure operation and governance. If the resources required to participate become too expensive, fewer independent operators may remain capable of running the system. Why is there a trade-off? Increasing block capacity, for example, may allow more transactions to be processed. However, larger blocks can require more bandwidth, storage and processing power. If ordinary participants cannot keep up, the network may become more dependent on operators with substantial infrastructure. This can create pressure toward centralisation. The trilemma is a useful architectural framework, but it should not be treated as a mathematical law proving that every blockchain must permanently sacrifice one of the three properties. Technological improvements, new cryptographic techniques and alternative architectures can change the available trade-offs. The important question is how a particular system achieves its performance and security objectives, and what assumptions or costs accompany those choices.

12.3 Security Is More Than Cryptography

Cryptography is essential to blockchain security, but cryptographic strength alone does not make a blockchain secure. A system may use strong digital signatures and cryptographic hashes while remaining vulnerable to other forms of attack. Security can be examined through several dimensions.

Cryptographic security

Protects signatures, hashes and commitments against specific forms of manipulation.

Consensus security

Protects the accepted chain against attempts to rewrite history, create invalid blocks or manipulate agreement.

Execution security

Ensures that transactions and smart contracts are processed according to the protocol rules.

Network security

Protects communication, peer discovery and information propagation against disruption and manipulation.

Economic security

Examines the costs, incentives and resources required to attack or control the network.

Implementation security

Concerns the correctness of the software that implements the protocol.

Operational security

Includes infrastructure protection, key management, monitoring, backups and incident response. A failure in any of these areas can affect the practical security of the overall system. For example, an attacker may not need to break a cryptographic algorithm if a software vulnerability allows a node to accept an invalid transaction. Likewise, a perfectly functioning blockchain cannot protect a user who voluntarily reveals a private key to a malicious party.

12.4 Consensus Security and the Cost of Attacks

Consensus mechanisms are designed to make manipulation of the accepted chain difficult. However, different consensus systems rely on different assumptions.

Proof of Work

In Bitcoin, an attacker attempting to replace accepted history must produce an alternative chain with sufficient accumulated proof of work. This requires computational resources and energy. The practical difficulty depends on the distribution of mining power, the attacker's resources, network conditions and the amount of work already accumulated by the accepted chain.

Proof of Stake

In Proof-of-Stake systems, security depends on stake distribution, validator behaviour, protocol rules and the economic consequences of misconduct. Ethereum and Cardano use different Proof-of-Stake designs, and their security assumptions should be evaluated separately. An attacker may attempt to influence validator participation, exploit protocol weaknesses or disrupt communication. The effectiveness and consequences of such attacks depend on the particular consensus protocol.

No consensus mechanism is independent of assumptions

A security analysis must ask:

  • How much influence can one participant obtain?
  • How is block production selected?
  • What happens when participants behave dishonestly?
  • How does the network handle temporary communication failures?
  • What economic penalties or costs apply to attacks?
  • How can the network recover from unexpected failures?

The existence of a consensus mechanism does not eliminate the need to analyse these questions.

12.5 The Limits of Independent Verification

Independent verification is one of the most important properties of a blockchain. A participant running a full node can check relevant blocks and transactions against the protocol rules rather than relying exclusively on a third party's report. However, independent verification has resource requirements. A node may need:

  • Sufficient storage for blockchain data and state.
  • Adequate processing capacity.
  • Reliable internet connectivity.
  • Memory for validation and execution.
  • Compatible and correctly maintained software.

As the network grows, these requirements may increase. If the cost of operating a node becomes too high, fewer independent participants may be able or willing to verify the network directly. This creates an important architectural question: Can the network increase capacity without making independent verification prohibitively expensive? Different blockchain systems answer this question differently. Bitcoin's full-node model prioritises independent validation, while its transaction capacity and block-space constraints reflect design choices concerning network resources. Ethereum has been developing scaling mechanisms that aim to increase capacity while maintaining important verification and security properties. Cardano's Ouroboros design also seeks to support permissionless participation through stake-based consensus and protocol-defined resource requirements. None of these approaches removes the need to monitor hardware requirements, software complexity and the distribution of actual network participation.

12.6 Scalability Has Several Dimensions

Scalability is often reduced to one number: transactions per second. This is an incomplete way to evaluate a blockchain. A network's performance includes several separate dimensions.

Throughput

How many transactions can the system process over a given period?

Latency

How long does it take for a transaction to be received, processed and included in a block?

Finality

How long does it take before the system considers a transaction settled according to its consensus rules?

Cost

How much does it cost to submit and execute a transaction?

Resource efficiency

How much computing power, storage, memory and bandwidth are required?

Verification accessibility

Can independent participants still verify the system without relying on a small number of specialised operators? These dimensions do not always improve together. A system may achieve high throughput but require powerful hardware. Another may offer inexpensive transactions through a separate execution layer while introducing additional dependencies on operators, bridges or data availability services. A meaningful scalability analysis must therefore consider the entire architecture, not only a headline performance figure.

12.7 Layer 2 and Modular Systems: New Opportunities, New Risks

Layer 2 systems and modular blockchain architectures can improve scalability by separating functions and distributing work. However, they also introduce additional security assumptions. A Layer 2 system may depend on:

  • An underlying settlement layer.
  • A data availability mechanism.
  • A sequencer or transaction ordering service.
  • A proof generation and verification system.
  • Smart contracts that manage deposits and withdrawals.
  • Cross-layer communication and bridge mechanisms.

These components can introduce different failure modes.

Sequencer centralisation

Some rollups initially rely on a single sequencer or a small group of operators. A sequencer may be able to delay transactions, censor users or become unavailable. Even if the rollup ultimately relies on Ethereum for settlement, its operational characteristics may still depend on the sequencer's availability and design.

Data availability

If the data needed to reconstruct the rollup's state is unavailable, users may be unable to independently verify activity or perform certain operations. Ethereum's documentation emphasises that data availability is essential for independent verification of rollup state transitions.

Proof systems

Optimistic and zero-knowledge rollups use different methods to establish the validity of state changes. Optimistic systems depend on mechanisms for detecting and challenging invalid state transitions. Zero-knowledge systems depend on the correctness of proof generation, verification and the relevant cryptographic assumptions.

Bridges and external dependencies

A bridge may hold or control assets while coordinating transfers between networks. If its contracts, validators, operators or verification mechanisms fail, users may lose access to transferred assets. The security of a Layer 2 or modular system must therefore be evaluated according to its actual implementation, not simply by the blockchain to which it is connected.

12.8 Smart Contracts and Application-Level Risk

A blockchain can operate correctly while an application built on top of it contains serious vulnerabilities. Smart contracts introduce additional logic and state transitions. A programming error can cause funds to become inaccessible, allow unauthorised operations or produce unintended results. Common categories of smart contract risk include:

  • Incorrect access control.
  • Reentrancy vulnerabilities.
  • Arithmetic and accounting errors.
  • Incorrect assumptions about external data.
  • Oracle manipulation.
  • Flawed liquidation or collateral logic.
  • Unsafe upgrade mechanisms.
  • Inadequate testing and review.

An oracle is a mechanism that provides external information to a smart contract. For example, a decentralised finance application may depend on an external price feed. The blockchain can correctly execute the contract according to its rules while the contract still produces an undesirable result because the external information is inaccurate or manipulated. This illustrates an important distinction: Blockchain consensus can establish agreement about execution, but it cannot guarantee that the application logic or external information is economically or logically correct. Security reviews must therefore examine both the underlying protocol and the applications that use it.

12.9 Network and Infrastructure Risks

A decentralised blockchain still depends on physical and digital infrastructure. Nodes require computers, electricity, network connections and software. Validators and miners may depend on hosting providers, data centres, internet service providers and other external services. This creates several possible risks:

Internet disruption

Network outages or connectivity problems can delay communication and block propagation.

Infrastructure concentration

If many participants rely on the same cloud provider or data centre, a single infrastructure failure can affect a substantial part of the network.

Denial-of-service attacks

Attackers may attempt to overwhelm nodes or other network services with excessive traffic or specially constructed messages.

Software vulnerabilities

A bug in a widely used client can have consequences beyond the individual operator running it.

Operational mistakes

Poor key management, insecure configurations and inadequate monitoring can expose participants to unnecessary risks. Decentralisation at the protocol level does not automatically guarantee decentralisation at the infrastructure level. A useful security assessment must therefore examine where nodes operate, how they communicate and whether important services depend on a limited number of providers.

12.10 Governance and the Risk of Concentrated Influence

Blockchain protocols evolve through technical and social coordination. Developers propose changes, researchers analyse them, node operators install software and other participants decide whether to support the resulting network. This creates another architectural dimension: governance. A network may have a technically decentralised consensus mechanism but still experience concentrated influence in other areas. For example:

  • A small number of organisations may maintain widely used software clients.
  • A limited group may control important infrastructure.
  • Large stakeholders may have disproportionate economic influence.
  • Application developers may depend on centralised service providers.
  • Users may have limited practical understanding of protocol changes.

These circumstances do not necessarily mean that a blockchain is centrally controlled. However, they demonstrate that decentralisation is not a single measurable property. It must be evaluated across several dimensions:

DimensionImportant question
ConsensusWho can influence block production and chain selection?
ValidationWho can independently verify the ledger?
EconomicHow concentrated are mining power, stake and rewards?
GovernanceWho influences protocol decisions and upgrades?
InfrastructureHow dependent is the network on specific providers?
ApplicationDo users depend on centralised interfaces or operators?

A complete assessment should examine how these dimensions interact.

12.12 The Importance of Measuring Real Security

Security claims should be supported by evidence and clearly defined assumptions. For example, a statement that a network is decentralised should not rely only on the number of addresses, validators or nodes. It should consider whether participants are genuinely independent and whether they have the ability to act separately. Likewise, a high transaction throughput figure should be examined alongside the hardware and network resources required to achieve it. Useful questions include:

  • How many independent participants validate the system?
  • What proportion of block production or stake is controlled by major operators?
  • Can users exit or recover assets if an operator becomes unavailable?
  • Can the network continue functioning during infrastructure failures?
  • Are critical components independently audited?
  • How are software vulnerabilities discovered and corrected?
  • Can users verify transaction data without relying on a single service?
  • What assumptions are required for the stated security guarantees?

The answers may change over time as software, network participation and infrastructure evolve. A blockchain's security is not a permanent label. It is a property that must be continuously assessed.

12.13 What Blockchain Architecture Cannot Guarantee

A technically sound blockchain can provide important guarantees, but it cannot solve every problem associated with digital systems. It cannot automatically guarantee:

The truth of external information

A blockchain can record information consistently without proving that the information was true when submitted.

The safety of every application

Smart contracts and decentralised applications may contain vulnerabilities even when the underlying network operates correctly.

The security of user devices

Malware, phishing and compromised devices can expose private keys.

The permanence of every external service

Websites, wallets, explorers, oracles and hosting providers may become unavailable.

Equal economic influence

A decentralised protocol does not automatically distribute wealth, mining power or stake equally.

Legal recognition

Technical execution does not determine how every jurisdiction treats an asset, transaction or contractual arrangement.

Perfect scalability

Increasing throughput and reducing costs can introduce new resource requirements and dependencies. These limits do not make blockchain technology useless. They clarify what blockchain systems are designed to do and which problems require additional technical, operational, legal or institutional solutions.

12.14 A Framework for Evaluating Blockchain Architecture

A useful evaluation should examine the entire system rather than focusing on a single feature. The following framework can be applied to an established blockchain, a new protocol or a Layer 2 system.

12.14.1 Network structure

  • How are nodes connected?
  • Who can participate?
  • Are important infrastructure services concentrated?

12.14.2 Data and state

  • How is ownership represented?
  • How is state updated?
  • Can independent participants reconstruct and verify the ledger?

12.14.3 Execution

  • How are transactions processed?
  • Are execution rules deterministic?
  • What resources are required?

12.14.4 Consensus

  • How are block producers selected?
  • How is the accepted chain determined?
  • What finality or settlement guarantees exist?

12.14.5 Security

  • What are the main attack scenarios?
  • What economic and cryptographic assumptions are required?
  • How are vulnerabilities discovered and corrected?

12.14.6 Scalability

  • What limits throughput?
  • What are the hardware and bandwidth requirements?
  • How does the system handle increased demand?

12.14.7 Governance

  • How are protocol changes proposed?
  • Who participates in decisions?
  • What happens when participants disagree?

12.14.8 External dependencies

  • Does the system depend on bridges, oracles, sequencers or third-party infrastructure?
  • What happens if those services fail?
  • Can users recover their assets or verify their positions independently?

This framework provides a more reliable basis for comparison than marketing claims or isolated performance statistics.

12.15 The Architectural Lesson: No Design Eliminates Every Trade-off

Blockchain technology is a collection of architectural solutions to difficult problems in distributed computing. Different networks make different decisions about how to represent state, organise transactions, coordinate participants, protect the accepted chain and support applications. Bitcoin, Ethereum and Cardano demonstrate that a blockchain does not need to follow one universal design. Their architectures differ, but each must address the same fundamental challenges:

  • How to maintain a consistent ledger.
  • How to prevent invalid state changes.
  • How to coordinate independent participants.
  • How to protect users and applications.
  • How to scale without undermining important security properties.
  • How to evolve without losing network compatibility.

Modular architectures and Layer 2 systems expand the available design possibilities, but they also introduce additional dependencies and coordination requirements. The most important lesson is that technological progress should not be measured by transaction speed or the number of features alone. A reliable blockchain architecture must be evaluated by the guarantees it provides, the assumptions on which those guarantees depend and the costs required to maintain them. Understanding these trade-offs is essential to understanding the real capabilities and limitations of digital infrastructure.

Key Takeaways

  1. Blockchain security is systemic. It depends on cryptography, consensus, execution, networking, software and operational practices.
  2. The blockchain trilemma describes tensions among security, scalability and decentralisation, but it is an architectural framework rather than an absolute mathematical law.
  3. Scalability is multidimensional. Throughput, latency, finality, transaction costs and independent verification all matter.
  4. Independent verification has resource requirements. Increasing hardware and bandwidth demands can create pressure toward infrastructure concentration.
  5. Layer 2 and modular architectures introduce additional dependencies, including sequencers, bridges, proof systems and data availability services.
  6. Smart contract security is separate from blockchain consensus security. A network can execute vulnerable application code correctly.
  7. Infrastructure decentralisation matters. Cloud providers, data centres and network services can create concentration risks.
  8. Governance influence is not identical to consensus participation. Different groups can have different forms of influence over a blockchain.
  9. No single metric establishes overall security or decentralisation. Evaluations require evidence across several dimensions.
  10. Blockchain architecture involves trade-offs. Its quality depends on how effectively it balances security, verification, performance and practical usability.

Research Note

The term secure blockchain should never be interpreted as a guarantee that every component, application or user interaction is free from risk. A blockchain protocol can provide specific technical guarantees under defined assumptions. Those guarantees do not automatically extend to external applications, bridges, wallets, oracles, infrastructure providers or legal arrangements. Likewise, scalability improvements must be evaluated alongside the resources and dependencies they introduce. A meaningful architectural assessment therefore asks not only what a blockchain can do, but also what it requires, what it assumes and where its limitations remain.
