SMART CONTRACTS & VIRTUAL MACHINES

From Programmable Logic to Decentralised Applications

How blockchain programs are written, deployed and executed — and how virtual machines, interfaces, external data and security shape the applications built around them.

INTRODUCTION

Smart contracts are among the defining capabilities of programmable blockchain systems. They allow network participants to interact with shared programs whose rules are enforced through protocol-defined execution rather than through the discretion of a single application operator. These programs can manage digital assets, record permissions, coordinate exchanges, represent ownership and connect multiple services into more complex systems.

Yet the expression smart contract can be misleading if it is understood too literally. A smart contract is not necessarily a legal agreement, an intelligent agent or an autonomous entity. It is software deployed within a blockchain environment. Its behaviour depends on code, transaction inputs, the current state of the network, the execution rules of the platform and, in many applications, information supplied by external systems.

This study follows the complete path from programmable logic to application: how contracts work, how virtual machines execute them, how developers compile and deploy code, how applications communicate with contracts, and how standards, oracles, economic incentives and security practices influence the result. Ethereum's EVM provides a central example, while alternative execution models demonstrate that programmable blockchains do not all use the same architecture.

Three distinctions to keep in mind

Smart contract ≠ legal contract. A program may implement contractual logic, but its existence does not automatically establish a legally enforceable agreement.

Virtual machine ≠ blockchain. A virtual machine executes instructions. The blockchain protocol coordinates transaction ordering, validation and the accepted state shared by network participants.

Automation ≠ guaranteed correctness. Code can execute exactly as written and still produce an unintended, unsafe or unfair result.

01. What Is a Smart Contract?

1.1 A Program That Lives at a Blockchain Address

In Ethereum, a smart contract is a program consisting of code and persistent data (its state) associated with a contract account at a blockchain address. Once deployed, the contract can be called by transactions from users or by other contracts. Its functions define which operations are available and under what conditions they may change the system's state.

The term is also used more broadly for programs on other programmable networks, although those networks may use different execution models and terminology. Solana, for example, commonly calls its on-chain programs simply programs. The underlying idea is similar — software executes according to network rules — but the account and state architecture differs.

1.2 What Makes It “Smart”?

The word “smart” refers primarily to the ability to encode rules and execute them automatically when specified conditions are met. A simple token contract might define how balances are recorded and how transfers are authorised. A lending protocol may calculate collateral ratios and determine whether a position can be liquidated. A voting contract may record proposals, verify voting permissions and count submitted votes.

None of these examples requires the program to think or understand human intentions. The program processes inputs according to explicit instructions. It does not independently decide whether those instructions are wise, lawful or socially desirable.

1.3 Code, State and Address

Three elements help explain a deployed contract:

  • Code: the instructions that define the contract's permitted operations.
  • State: the data that the program maintains, such as balances, ownership records, configuration values or proposal status.
  • Address: the network identifier through which transactions and other contracts can refer to the deployed program.

On Ethereum, contract code is stored as bytecode and its persistent storage contributes to the global state. A transaction may execute the code and, if it succeeds, update that state. A read-only query can inspect data without creating a state-changing transaction.

1.4 What a Smart Contract Is Not

A smart contract is not inherently a legal contract, a company, a human agent or a guarantee that an exchange will be fair. It cannot automatically verify every fact about the physical world. Nor does decentralised execution mean that the software has no administrators, privileged keys, upgrade mechanisms, dependencies or points of failure. These properties must be examined in each system.

Working definition

A smart contract is a program deployed in a blockchain's execution environment that processes authorised inputs according to defined rules and may change the network state when its execution is accepted.

02. From Agreements to Programmable Logic

2.1 The Idea of Encoding Rules in Software

The idea of translating agreements and procedures into computer-executable rules predates blockchain technology. Businesses have long used software to automate payments, inventory, settlement, access permissions and conditional workflows. A computer can apply a rule consistently, provided that the rule is represented in a form the system can process and the required data is available.

In the 1990s, computer scientist and legal scholar Nick Szabo developed the concept of “smart contracts” to describe computerised transaction protocols that execute the terms of an arrangement. His work explored how digital systems could formalise commitments and reduce the need for some forms of manual coordination. The concept did not require a blockchain: it concerned the relationship between contractual logic and computation.

2.2 Why Earlier Automation Was Not the Same as a Public Smart Contract

Traditional automated systems generally operate within an organisation's infrastructure. The organisation controls the database, application code and access permissions, and users rely on its operational and legal framework. This can be entirely appropriate, but the operator remains a central point of administration.

Public blockchains introduced a different arrangement. A program can be deployed to a shared network, where independent nodes apply common execution rules and verify state transitions. Users can inspect deployed code and submit transactions without asking one application company to update a private database on their behalf. This changes the trust and governance model, although it does not eliminate all intermediaries or dependencies.

2.3 Ethereum and General-Purpose On-Chain Execution

Bitcoin Script supports conditions that determine whether transaction outputs can be spent. It is intentionally limited compared with a general-purpose programming environment. Ethereum extended the idea of programmable transactions by introducing an account-based state machine and the Ethereum Virtual Machine. Developers could deploy programs with persistent state and expose functions that users and other contracts could call.

This made possible a broad ecosystem of tokens, decentralised exchanges, lending protocols, collectibles, governance systems and other applications. Other networks later developed their own approaches to programmable execution. The result is not one universal smart-contract architecture, but a family of systems with different design choices.

2.4 From Human Agreements to Executable Specifications

Turning an agreement into software requires translating human language into precise conditions. Consider a simple escrow arrangement: funds are held until a specified event occurs, after which they are released to one party or returned to another. A programmer must decide how the parties are identified, which event counts as proof, who can submit that proof, what happens if a deadline passes and how disputes are handled.

Every such decision is a design choice. Ambiguity in the original arrangement cannot be solved merely by writing code. If the program has no procedure for an exceptional situation, it may become stuck or produce a result that the participants did not anticipate.

03. How Smart Contracts Work

3.1 A Transaction as a Request for Execution

A common interaction begins when a user selects an action in an application. The application prepares transaction data describing the target contract, the function to call and the encoded arguments. A wallet presents the transaction for review and, when approved, signs it with the user's key. The signed transaction is submitted to a network node or transaction service and may be propagated, included in a block and executed under the protocol's rules.

3.2 Function Calls and Input Data

A contract exposes functions with defined inputs and behaviour. For example, a token transfer function may accept a recipient address and an amount. The contract checks relevant conditions — such as whether the caller has sufficient balance — and then performs the specified state changes if the checks pass.

On Ethereum, a contract call is commonly identified by a four-byte function selector derived from the function signature, followed by encoded arguments. The ABI defines the conventions used to encode and decode this data. Other platforms use their own instruction and interface formats.

3.3 Execution and State Transition

Nodes execute transactions according to the same protocol rules. In a successful state-changing call, the execution may update account balances, contract storage or other state. A transaction can also emit logs, which applications and indexing services can use to detect events. The network's consensus and block-validation process determines which transactions form part of the accepted chain and in what order.

Execution is deterministic within a given protocol context: the same valid transaction applied to the same pre-state under the same rules must produce the same result. Determinism is essential because independent nodes must be able to verify the same state transition. This does not mean that every transaction is guaranteed to succeed. A call may revert because a condition is not met, run out of gas or fail for another protocol-defined reason.

3.4 Read Operations and State-Changing Operations

On Ethereum, a read-only call can be simulated by a node without submitting a transaction that changes the canonical state. Such a query is often called a call and is commonly used to retrieve balances or inspect contract values. A state-changing operation requires a transaction to be signed and included in a block. It consumes execution resources and is subject to transaction fees.

3.5 A Simple Illustrative Sequence

  1. A user requests a token transfer in a dApp.
  2. The dApp encodes the recipient and amount using the contract's ABI.
  3. The wallet displays the transaction details and requests authorisation.
  4. The signed transaction is submitted to the network.
  5. Nodes execute the contract code and check its conditions.
  6. If execution succeeds and the transaction is accepted, the relevant balances change in the network state.
  7. The application reads the resulting state or event and updates its interface.

This sequence is simplified. Real applications may involve multiple contracts, relayers, account-abstraction services, bridges, oracles and off-chain infrastructure. Each additional component introduces assumptions that should be understood separately.

04. The Ethereum Virtual Machine (EVM)

4.1 The EVM as a Shared Execution Environment

The Ethereum Virtual Machine is the execution environment that defines how Ethereum contract bytecode behaves. It is not a physical computer located in one place. It is a protocol-defined virtual machine implemented by Ethereum clients. Nodes execute transactions using these rules so that they can independently derive and verify the resulting state.

The EVM provides a controlled environment for executing contract code. Contract execution does not have unrestricted access to a node's operating system, filesystem or arbitrary network connections. This isolation helps make execution predictable and prevents a contract from simply behaving like an ordinary server-side application.

4.2 From Bytecode to Opcodes

Developers usually write contracts in a higher-level language such as Solidity or Vyper. A compiler translates the source code into EVM bytecode. Bytecode is a sequence of instructions, often described as opcodes, that the EVM interprets. Examples include arithmetic operations, comparisons, memory operations, storage access, control flow and calls to other contracts.

The EVM maintains a program counter that identifies the next instruction. As execution proceeds, the machine reads instructions, processes values and updates its temporary execution context. The code is not executed by a single central Ethereum computer; each validating execution client applies the rules locally.

4.3 Stack, Memory and Persistent Storage

The EVM is a stack machine. Many instructions take values from a stack and place results back onto it. Each stack item is a 256-bit word, and the stack has a protocol-defined maximum depth. The stack is temporary working space for the current execution.

Memory is a temporary, byte-addressable area used during execution. It expands as needed and is cleared when the execution frame ends. Storage is different: it is persistent key-value data associated with a contract account and forms part of Ethereum's world state. Writing to persistent storage is generally much more resource-intensive than simple arithmetic or stack operations.

Three different kinds of data

Bytecode: the deployed program instructions.

Machine state: temporary execution information such as the program counter, stack, memory and remaining gas.

Contract storage: persistent values that survive successful execution and become part of the blockchain state.

4.4 Determinism and the World State

The EVM executes a transaction against a defined pre-state and transaction context. Its rules specify which operations are permitted and how they affect the resulting state. If execution succeeds, the resulting changes are included in the state transition validated by the network. If execution reverts, the state changes from the reverted execution frame are discarded, although the transaction may still consume gas and remain recorded as a failed transaction.

4.5 The EVM Is Not the Whole Ethereum Network

The EVM defines execution semantics, but Ethereum also needs networking, transaction propagation, consensus, data availability, clients and state storage. The execution layer processes transactions and computes state changes; the consensus layer coordinates block proposals and agreement on the chain. Treating the EVM as synonymous with Ethereum obscures these distinct responsibilities.

05. Smart Contract Programming Languages

5.1 Source Code and Compilation

Most developers do not write EVM bytecode directly. They use a higher-level language, compile the source code and deploy the resulting bytecode. The compiler also produces supporting information, commonly including an ABI and metadata that help tools identify functions, events, compiler settings and source files.

5.2 Solidity

Solidity is a statically typed, high-level language designed primarily for writing smart contracts that target the EVM. Its syntax is influenced by several familiar programming languages. It supports functions, data structures, inheritance, libraries, events, modifiers and custom types. Solidity is widely used across Ethereum and EVM-compatible networks.

Solidity's familiarity does not make it automatically safe. Developers must understand visibility, storage layout, external calls, arithmetic behaviour, access control and the semantics of the EVM. Compiler version and settings also matter: bytecode depends on the exact compilation environment.

5.3 Vyper

Vyper is another high-level language that targets the EVM. It emphasises readability, simplicity and a more restricted language design. Its features and syntax differ from Solidity, and it is not simply a Python version of Solidity. Choosing a language involves developer expertise, ecosystem tooling, auditability and the requirements of the application.

5.4 Yul and Lower-Level Development

Yul is an intermediate language used in the EVM development toolchain and can also be used for lower-level programming. It gives developers more direct control over EVM operations, but that control demands a deeper understanding of execution details. Lower-level code can be useful for specialised optimisation, yet it can also increase the difficulty of review and maintenance.

5.5 Compilation Is Part of the Security Boundary

Source code alone does not fully identify what was deployed. Reproducible verification requires attention to the compiler version, optimisation settings, imported dependencies, linked libraries and constructor parameters. Publishing verified source code helps users compare human-readable code with deployed bytecode, but verification does not prove that the design is secure or that the application behaves as users expect.

06. Beyond EVM: Alternative Execution Environments

6.1 Why Different Networks Choose Different Models

Not every blockchain uses the EVM. Different platforms make different decisions about programming languages, account models, state access, parallel execution, resource metering and upgrade procedures. These decisions affect how developers structure applications and how users interact with them. A comparison should therefore examine the complete execution model rather than rank platforms using one headline metric.

6.2 Solana: Programs and Separate Data Accounts

Solana commonly describes smart contracts as programs. A program is deployed as executable bytecode in an account, while mutable application state is stored in separate data accounts passed to the program through instructions. Programs are designed to be stateless in the sense that mutable state is not stored inside the executable program account itself.

This separation is an important architectural contrast with Ethereum's contract-account model, where a contract account has code and associated persistent storage. Solana transactions and instructions identify the accounts they will read or modify. Explicit account access helps the runtime determine which operations may be scheduled in parallel, subject to account conflicts and other execution constraints.

6.3 Solana's sBPF Runtime

Solana programs are compiled to Solana Bytecode Format (sBPF), a Solana-specific variant of eBPF bytecode, and executed in a sandboxed runtime. Rust is a prominent development language, with frameworks and libraries that help developers work with the account and instruction model. The runtime enforces compute and memory constraints, validates account access and defines how programs invoke other programs.

It is important not to describe Solana's sBPF as identical to standard eBPF or to assume that every WebAssembly-based blockchain uses the same runtime. Similar names or shared compiler technologies do not make execution semantics interchangeable.

6.4 WebAssembly (WASM)

WebAssembly is a portable binary instruction format and execution environment originally standardised for safe, efficient execution across different platforms, especially in web environments. It is not itself a blockchain or a complete smart-contract platform. Blockchain projects may adopt WebAssembly or a related runtime as part of their execution architecture, but they must still define host functions, storage, transaction rules, resource metering, permissions and consensus integration.

WASM can allow developers to use languages that compile to the format, depending on the platform's supported toolchain and runtime. However, a WASM module running in a browser and a WASM-based smart contract running in a blockchain are not automatically equivalent: the blockchain host environment defines what the module can access and how its effects are validated.

6.6 No Universal Winner

Different execution models make different trade-offs. The EVM has a mature ecosystem, broad tooling and established standards. Solana's explicit account model and runtime are designed around a different approach to state access and transaction scheduling. WASM offers a portable instruction format, but the properties of a blockchain implementation depend on its host environment and protocol. Performance, security and decentralisation cannot be inferred from the virtual-machine label alone. They require measurements and analysis of the complete system under comparable conditions.

07. Gas, Computation and Execution Costs

7.1 Why Computation Needs a Meter

Public blockchain nodes spend computing resources to validate and execute transactions. If execution were unlimited or free, a user could submit a program that consumes excessive resources or never terminates, making it difficult for nodes to process other transactions. A resource-metering system limits the work that can be requested and assigns costs to operations.

7.2 Gas in Ethereum

Ethereum uses gas as a unit that measures the computational and other protocol-defined resources consumed by transaction execution. Different operations have different gas costs. A transaction specifies a gas limit, which bounds the amount of gas that can be consumed. If execution exhausts the available gas, it fails and state changes from the reverted execution are not committed.

Gas is not the same thing as ether. Gas measures resource use; the transaction fee is paid in ETH according to the applicable fee rules. Under Ethereum's post-London fee market, a transaction's effective price reflects a base fee and, where applicable, a priority fee, subject to the transaction's fee settings. Exact fee conditions change with network demand and protocol rules, so a fixed gas amount should not be confused with a fixed monetary cost.

7.3 Why Storage and External Calls Matter

Operations that modify persistent state generally consume more resources than simple arithmetic. Storage writes require changes to the state that nodes must maintain and verify. External contract calls also introduce execution work and additional trust assumptions. A developer must therefore consider not only whether a function is logically correct but also whether its resource use is predictable and bounded.

7.4 Block Limits and Denial of Service

Block-level resource limits constrain how much execution work can be included in a block. This helps nodes estimate and manage validation requirements. Poorly designed contracts can still create denial-of-service risks for their own users or dependent protocols — for example, by requiring an unbounded loop over a growing list of entries. A function that becomes too expensive to execute may become practically unusable even if it remains technically valid.

7.5 Other Networks Use Other Metering Systems

Gas is an Ethereum term and should not be used as if every blockchain applies precisely the same accounting model. Solana, for example, uses compute units and transaction resource limits. Other platforms define their own fees, execution budgets and storage costs. The general principle is shared: network resources are scarce and must be metered, but the units and economic rules are protocol-specific.

08. Contract Deployment and Lifecycle

8.1 Development and Testing

A contract normally begins as source code in a development environment. Developers compile it, run unit and integration tests, inspect static-analysis results and test interactions with other contracts. More mature processes may include fuzz testing, invariant testing, formal verification of selected properties, independent code review and audits. No single test method can establish the absence of all defects.

8.2 Deployment as a Transaction

On Ethereum, deployment is initiated through a contract-creation transaction. The transaction includes creation bytecode and any constructor arguments. The EVM executes the creation code, and if deployment succeeds, the resulting runtime bytecode is stored at the new contract address. The address is derived according to the protocol's contract-creation rules. Deployment consumes gas and becomes part of the blockchain's history when included in an accepted block.

8.3 Verification and Publication

After deployment, a project may publish the source code and compiler metadata and verify that they reproduce the deployed bytecode. This improves transparency and allows users to inspect the implementation. Verification is not a security certificate: it shows correspondence between published source and deployed code under specified compilation settings, not that the code is free of vulnerabilities or that the project's claims are accurate.

8.4 Immutable Code and Upgrade Patterns

Many blockchain contracts are difficult or impossible to modify after deployment. This can provide predictability: users can inspect the code and know that its logic will not silently change through an ordinary database update. However, immutability can also make defects difficult to repair.

Some systems use proxy patterns or other upgrade mechanisms. A proxy can keep an address and storage while delegating execution to a separate implementation contract. An authorised account or governance process may change the implementation address. This flexibility introduces additional risks: who controls upgrades, how changes are announced, whether storage layouts remain compatible and whether users can exit before a change takes effect.

8.5 Pausing, Deactivation and Lifecycle Management

Some contracts include emergency pause functions, role-based administration or mechanisms that restrict future operations. Others are intentionally immutable. A pause mechanism can limit damage during an incident, but it also creates privileged control and can itself become a target. A contract's lifecycle therefore includes governance and operational decisions, not just the initial deployment transaction.

Questions to ask before interacting with a deployed contract

  • Is the source code verified and does it match the deployed bytecode?
  • Can the contract be upgraded, paused or administratively controlled?
  • Who holds the relevant keys or governance permissions?
  • Are external libraries, oracles or other contracts critical dependencies?
  • Is there a documented response process for vulnerabilities?

09. Application Binary Interface (ABI)

9.1 Why an Interface Is Needed

A deployed contract is bytecode, not a graphical form with labelled buttons. An application needs a precise way to identify the functions and events available and to encode the values expected by those functions. On Ethereum, this role is served by the Application Binary Interface, or ABI.

9.2 What an ABI Describes

An ABI describes a contract's externally accessible functions, their input and output types, and the events the contract can emit. It also defines encoding conventions that allow software to translate structured values into the byte sequences used in transactions and calls, and to decode returned data and logs.

9.3 Function Selectors and Encoded Arguments

For a typical external Solidity function, the first four bytes of the call data identify the function selector. The selector is derived from the Keccak-256 hash of the canonical function signature. The encoded arguments follow according to ABI rules. The selector is a compact identifier, not a cryptographic proof that the function is safe or that the address belongs to the project a user expects.

9.4 ABI and Application Compatibility

Front-end libraries use an ABI to prepare calls and interpret results. If the ABI does not match the deployed contract, the application may encode the wrong data, fail to decode a response or call an unintended function. For proxy systems, developers must also account for the relationship between the proxy address, implementation and the ABI expected by the current implementation.

9.5 ABI Is Not the Same as Source Code

An ABI describes an interface; it does not reveal the full internal logic of a contract. Two contracts can expose similar ABIs while behaving very differently. A user interface should therefore not treat a familiar function name as proof of trustworthy behaviour. ABI inspection is one part of contract analysis, not a substitute for source review and transaction understanding.

10. Decentralised Applications (DApps)

10.1 A DApp Is More Than a Smart Contract

A decentralised application, or dApp, combines on-chain programs with user-facing and supporting software. A typical application may include a browser interface, wallet connection, contract addresses and ABIs, blockchain nodes or RPC providers, indexing services, storage systems and external data sources. Only some of these components necessarily run on-chain.

10.2 The Main Components

  • Front end: the interface through which users view information and request actions.
  • Wallet: manages keys or signing authority and presents transaction requests for user approval.
  • Smart contracts: implement on-chain rules and state transitions.
  • RPC provider or node: relays requests to the network and returns blockchain data.
  • Indexer: organises blockchain events and records into data structures that are easier for applications to query.
  • Off-chain services: may provide content, notifications, analytics, storage or other functions.

10.3 Wallets and Transaction Authorisation

A wallet is not simply an account balance display. It helps users manage signing keys or connect to a signing service. When a dApp requests a transaction, the wallet should show relevant information such as the target network, destination address, value and requested permissions. Users should verify these details carefully. A malicious interface can attempt to persuade a user to sign a transaction that grants broad token approval or transfers assets to an unintended address.

10.4 RPC Providers and Infrastructure Dependence

Many dApps use remote procedure call (RPC) endpoints to read blockchain data and submit transactions. An application may offer several providers or allow users to connect their own node. If an application depends on one provider, that provider can become an availability, privacy or censorship risk even when the underlying blockchain is decentralised. An RPC response is data supplied by infrastructure; critical actions should be validated against the network and relevant contract state.

10.5 What “Decentralised” Can Mean

The term dApp does not guarantee that every part of an application is decentralised. The front end may be hosted on a conventional server, an indexer may be operated by one company, an administrator may control upgrades, or a small number of signers may govern a treasury. A serious evaluation examines decentralisation component by component: execution, data, hosting, governance, access and operational control.

11. Oracles and the Limits of On-Chain Knowledge

11.1 The Boundary Between On-Chain and Off-Chain Information

A blockchain can verify information that is represented within its own protocol and state. It cannot independently observe the weather, a company's revenue, a sports result or the current market price on an external exchange. Smart contracts do not have unrestricted internet access. If a contract needs information from outside the chain, that information must be brought into the blockchain through an external mechanism.

11.2 What Is an Oracle?

An oracle is a system that supplies external data or computation to a smart contract. An oracle may retrieve information from one or more sources, aggregate it, sign a report and make it available on-chain. Applications use oracle data for functions such as collateral valuation, settlement, insurance triggers and event-based payments.

11.3 The Oracle Problem

The contract can verify that a submitted report follows the expected cryptographic and interface rules, but it cannot automatically prove that the underlying real-world information is true. If an oracle reports an incorrect price, a contract may execute its logic perfectly while producing a harmful outcome. The security of the application therefore depends on the quality, independence, availability and manipulation resistance of the data process.

11.4 Oracle Design and Trust Assumptions

Oracle architectures vary. Some use a single data provider; others aggregate multiple sources or use networks of independent node operators. Some rely on cryptographic proofs, threshold signatures, challenge periods or economic incentives. Each approach has different assumptions and failure modes. Multiple data sources can reduce dependence on one source, but aggregation does not automatically eliminate correlated errors or market manipulation.

11.5 Other External Dependencies

Oracles are not limited to prices. Contracts may depend on random-number services, cross-chain messaging, off-chain computation, identity attestations or data availability services. Each dependency should be included in the application's threat model. The more a contract relies on external systems, the less meaningful it is to assess the contract code in isolation.

12. Standards and Composability

12.1 Why Shared Standards Matter

Standards define common interfaces and behaviours that allow independent applications and contracts to interact. Without shared conventions, every wallet, exchange or application would need custom logic for every token or asset implementation. Standards reduce integration friction, but they do not guarantee that every implementation is secure or economically sound.

12.2 ERC-20: Fungible Tokens

ERC-20 defines a widely used interface for fungible tokens on Ethereum. Fungible units are intended to be interchangeable: one unit of a given token is treated as equivalent to another unit of the same token. The standard describes functions and events for balances, transfers, allowances and delegated transfers. Implementations may add features, restrictions or administrative controls beyond the basic interface.

12.3 ERC-721: Non-Fungible Tokens

ERC-721 defines an interface for non-fungible tokens, where each token has a distinct identifier within a contract. It supports ownership queries, transfers and approval mechanisms. The standard establishes an interface for tracking token ownership; it does not, by itself, determine the legal status of an associated artwork, the permanence of linked metadata or the copyright rights held by a token owner.

12.4 ERC-1155: Multi-Token Contracts

ERC-1155 provides a multi-token interface that can represent multiple token types within one contract. It supports both fungible and non-fungible token patterns and includes batch operations. This can reduce the need to deploy separate contracts for every asset type in applications such as games and digital collectibles.

12.5 Composability

Composability means that contracts can call other contracts and build on shared interfaces. A decentralised exchange may interact with token contracts, a lending protocol may use price feeds and token interfaces, and a wallet may use standard approval and transfer functions. This modularity allows developers to combine existing building blocks rather than recreate every feature.

12.6 Composability Also Propagates Risk

When one protocol depends on another, a vulnerability or failure can spread through the dependency chain. A token may change its behaviour, an oracle may become unavailable, a bridge may be compromised or an upgrade may alter an interface. Integrations should therefore document dependencies, monitor changes and define limits on the damage that a failure can cause.

13. Security, Vulnerabilities and Audits

13.1 Security Begins With Design

Smart-contract security is not a final checklist applied after coding. It begins with a clear specification of intended behaviour, trust assumptions, privileged roles, assets at risk and failure scenarios. Developers should identify what must always remain true — known as invariants — and test whether every function preserves those properties.

13.2 Reentrancy

Reentrancy can occur when a contract makes an external call and control passes to another contract before the original operation has safely completed. The called contract may call back into the first contract while its state is still in an intermediate condition. If the original contract has not updated or protected its state appropriately, the repeated call may exploit that inconsistency. Defensive design includes checks-effects-interactions, reentrancy guards where appropriate and careful review of every external interaction.

13.3 Access-Control Failures

Functions that mint tokens, withdraw funds, change parameters or upgrade implementations often require restricted permissions. If a sensitive function is publicly callable by mistake, or if role administration is incorrectly configured, an attacker may gain control over critical operations. Role-based access control, multisignature administration, timelocks and clearly documented privilege boundaries can reduce some risks, but each mechanism must be implemented and governed correctly.

13.4 Oracle and Economic Manipulation

Contracts that rely on prices or other external values can be vulnerable if an attacker can manipulate the data source or the market used to calculate it. Flash loans can amplify certain attacks by allowing an attacker to temporarily obtain substantial liquidity within one transaction, but flash loans are not inherently malicious. The vulnerability lies in protocol assumptions that can be manipulated through temporary capital, market structure or transaction ordering.

13.5 Logic Errors, Input Validation and External Calls

A contract can be syntactically correct yet implement the wrong business logic. Incorrect reward calculations, missing boundary checks, unsafe assumptions about token behaviour and unchecked external-call results can all cause failures. Developers must validate inputs, handle errors and avoid assuming that every external contract behaves exactly like a familiar reference implementation.

13.6 Arithmetic and Resource Risks

Integer overflow and underflow occur when arithmetic results exceed the range of a fixed-size integer type. Modern Solidity versions include checked arithmetic by default for ordinary arithmetic operations, but unchecked blocks, assembly, casts and logic errors still require care. Unbounded loops, expensive storage operations and attacker-controlled iteration can also make functions too costly or impossible to execute within resource limits.

13.7 Audits, Testing and Formal Methods

A smart-contract audit is an independent review of code, architecture and assumptions. It can identify vulnerabilities and recommend improvements, but it is not a guarantee that no defect exists. A useful security process may combine:

  • unit and integration tests;
  • fuzz testing with many generated inputs;
  • invariant and property-based testing;
  • static analysis and automated vulnerability scanners;
  • manual review of business logic and dependencies;
  • formal verification of selected critical properties;
  • independent audits, bug bounties and post-deployment monitoring.

13.8 Security Is a Continuous Process

After deployment, projects must monitor privileged actions, contract events, oracle behaviour, dependencies and unusual transactions. They should have an incident-response plan and communicate clearly with users. The security of an application is not fixed permanently at the moment an audit report is published: code, infrastructure, markets and attacker techniques continue to change.

Audit literacy

When reading an audit report, check which commit or deployed version was reviewed, what was excluded from scope, whether findings were fixed, whether fixes were re-reviewed and whether the current deployment matches the reviewed code. The word “audited” without these details provides limited information.

14. Economic and Legal Dimensions

14.1 Programmable Rules and Economic Incentives

Smart contracts can coordinate transfers, collateral, rewards, fees and governance rules. These mechanisms create economic incentives that influence how users, validators, liquidity providers, developers and administrators behave. A protocol's outcomes depend not only on code correctness but also on market conditions, strategic behaviour, liquidity, information quality and the distribution of control.

14.2 Automation Does Not Remove Governance

Many protocols include administrative roles, upgrade keys, emergency controls, governance votes or off-chain decision processes. Even if routine operations are automated, people and institutions may still decide how the system evolves, how incidents are handled and which changes are adopted. A credible analysis should distinguish automated execution from the governance arrangements surrounding it.

14.3 Code and Legal Agreements Are Different Systems

A program can encode obligations or payment conditions, but legal enforceability depends on the applicable law and facts. Relevant questions may include whether the parties intended to create legal relations, whether there was valid consent, how the parties are identified, what disclosures were made, which jurisdiction applies and what remedies are available. These questions cannot be answered merely by inspecting bytecode.

A legal agreement may refer to a smart contract as a method of performance or settlement. Conversely, a smart contract may operate without being the complete legal expression of the parties' relationship. The relationship between code and legal documentation must be assessed in context.

14.4 Responsibility and Consumer Protection

Responsibility may involve developers, protocol operators, interface providers, custodians, token issuers, governance participants or other actors, depending on their actual roles and the applicable legal framework. The fact that a transaction is technically irreversible does not automatically remove legal rights or obligations. Nor does calling a service decentralised determine its legal classification.

14.5 Regulatory Frameworks Are Jurisdiction-Specific

Rules for crypto-assets, financial services, consumer protection, data protection, sanctions and electronic contracting differ across jurisdictions and may change over time. In the European Union, for example, the Markets in Crypto-Assets Regulation (MiCA) establishes a framework for specified crypto-asset activities and service providers, but it does not make every smart contract or decentralised application automatically regulated or exempt. Scope depends on the relevant activity, entity, asset and legal provisions.

This section is educational, not legal advice. Anyone designing or using a system with material legal or financial consequences should consult qualified professionals in the relevant jurisdiction.

15. Key Takeaways and Research Sources

15.1 Key Takeaways

  • A smart contract is software deployed within a blockchain execution environment; it is not necessarily a legal contract or an intelligent agent.
  • The virtual machine defines how program instructions execute, while the blockchain protocol coordinates transaction ordering, validation and shared state.
  • Ethereum's EVM is a deterministic, gas-metered stack machine with temporary execution memory and persistent contract storage.
  • Solidity and Vyper are programming languages; EVM bytecode is the executable format interpreted by the EVM.
  • Alternative environments such as Solana's sBPF runtime and blockchain-specific WASM systems use different state and execution models.
  • Gas and other resource meters limit computation and help account for scarce network resources.
  • ABIs and token standards make integration easier, but an interface does not prove that an implementation is safe.
  • dApps combine on-chain contracts with wallets, interfaces, RPC infrastructure, indexers and sometimes external services.
  • Oracles connect contracts to off-chain information but introduce data-quality and trust assumptions.
  • Audits and testing reduce risk; they do not guarantee that a system is free of vulnerabilities.
  • Economic incentives, governance and legal obligations remain important even when execution is automated.

Research Perspective

Smart contracts make programmable rules available within shared digital infrastructure. Their significance lies not simply in automating transactions, but in creating systems where software, economic incentives, data sources and governance arrangements interact. Understanding those relationships — and their limits — is essential to evaluating the role of smart contracts in the evolving digital economy.
